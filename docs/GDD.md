## 0. 한 줄 요약

플레이어는 5×5 성단(星圖)에 **남십자자리의 별 조각**을 놓아 **황도 12궁**을 완성하고,
딜러 **иєвυℓα**와 거래하며 공허를 강화한다. 플레이 중에는 **ORION(M42)**이 곁에서 해설한다.
매 순간의 선택은 **확률 판단**이며, 게임은 그 판단이 옳았는지를 **통계로 되돌려준다.**

## 1. 학습 목표 (교과 연계)

### 1-2. ★ 중학생의 선수학습 (교과서가 직접 명시한 '배운 내용')

교과서는 각 대단원 도입부에 중학교 연계 내용을 명시한다. **이 게임의 난이도 기준선이다.**

| 학년 | 이미 배운 내용 | 게임에서 활용 |
|---|---|---|
| **중1** | 대푯값 / **도수분포표와 상대도수** | CONSTELLATION LOG의 상대도수 그래프 |
| **중2** | **경우의 수와 확률** | STAR-CHART, ORION'S WAGER의 기반 |
| **중3** | 산포도 / 상자그림과 산점도 | 점수 분포 시각화 |

> 🎯 **설계 원칙 확정**
> 중학생은 이미 **경우의 수·확률(중2)** 과 **상대도수(중1)** 를 배웠다.
> 따라서 이 게임은 *모르는 것을 가르치는 게* 아니라,
> **이미 아는 것(상대도수·확률)을 고교 개념(통계적 확률·기댓값)으로 잇는 다리**여야 한다.
> 부스에서 학생이 "아, 중학교 때 배운 그거네!"라고 말하게 만드는 것이 목표.

### 1-3. 게임 시스템 ↔ 성취기준 매핑

| 게임 시스템 | 대응 단원 | 성취기준 요지 (요약) |
|---|---|---|
| 공허 50장에서 8장 드로우 | Ⅰ-1, 중2 경우의 수 | 경우를 체계적으로 세는 방법 |
| STAR-CHART 실시간 패널 | **Ⅱ-1 확률의 뜻** | 확률의 개념과 기본 성질 설명 |
| ORION'S WAGER (기초) | **Ⅱ-2 확률의 덧셈정리** | 여사건의 확률을 활용해 문제 해결 |
| ORION'S WAGER (심화) | **Ⅱ-3 조건부확률** | 조건이 주어졌을 때의 확률을 실생활과 연결 |
| 매 턴 독립 드로우 | **Ⅱ-4 사건의 독립과 종속** | 독립·종속을 판단 |
| **DRIFT ORACLE** | **Ⅲ-2 기댓값** | 이산확률변수의 기댓값(평균)을 구함 |
| 동반성 티어 확률표 | Ⅲ-1 확률변수와 확률분포 | 확률분포의 뜻을 설명 |
| 공허 반환 vs 비복원 성운 | **Ⅲ-5 모집단과 표본** | 복원추출·비복원추출, 표본추출 방법 |
| **CONSTELLATION LOG** | **Ⅱ-1 통계적 확률 + Ⅲ-3 큰수의법칙** | 시행을 충분히 반복하면 상대도수가 수학적 확률에 접근 |
| 공허 빌딩 (칩 추가/제거) | Ⅲ-6 모비율 | 표본비율과 모비율의 관계 |

### 1-4. 교과서 반영 필수 수정 사항 ⚠️

교과서를 정독한 결과 **기존 설계에서 반드시 고쳐야 할 3가지**:

**① 용어 표기**
교과서는 **`큰수의법칙`** 으로 붙여 쓴다(띄어쓰기 없음). 게임 내 모든 표기를 통일한다.
또한 이 개념은 확률 단원이 아니라 **Ⅲ-3 이항분포**의 학습 요소다.

**② `비복원추출`의 단원 위치**
조건부확률(Ⅱ-3)이 아니라 **Ⅲ-5 모집단과 표본**에 속한다.
따라서 STAR-CHART의 설명 문구는 "조건부확률"이 아니라 **"표본추출"** 맥락으로 쓴다.

**③ ★ 조건부확률 문제 설계 — 교과서의 명시적 경고**
교과서 지도상의 유의점은, 조건부확률을 **조건이 주어진 상황의 가능성**으로 이해시키되
**사건의 시간적 순서나 인과관계로 해석하지 않도록** 하라고 못박고 있다.

| | 문구 |
|---|---|
| ❌ **금지** | "Acrux가 **이미 3장 나갔다. 이제** Ginan이 더 나올까?" → 시간적 순서 유도 |
| ✅ **수정** | "**지금 공허가 이 상태일 때**, Ginan이 Acrux보다 많이 나올까?" → 조건 상태 제시 |

기존 8-2절의 주기 6–8 예시 문구는 이 원칙에 따라 전량 재작성한다.

### 1-5. 게임 테마 문장

교과서 Ⅱ단원의 핵심 아이디어는 확률을 **합리적 의사 결정의 도구**로 규정한다.
이 문장이 Sirius의 정체성과 정확히 일치하므로, **게임 타이틀 화면과 부스 배너의 태그라인**으로 사용한다.

> *"확률은 운을 예측하는 것이 아니라, 더 나은 선택을 하는 도구다."*

### 1-6. 보너스 소재 (선택)

교과서 Ⅱ단원 '미래 수학 유니버스'에 **몬티 홀 문제**가 실려 있다.
ORION의 특별 이벤트("세 개의 성운 중 하나에만 보상이 있다")로 재현하면
교과서와의 연계를 심사에서 직접 증명할 수 있다. → Phase 6에서 검토

### 2-3. ★ 용어 대응표 (BOOTH-9a 확정) — **절대 규칙**

화면에 나가는 모든 문자열·문항·해설·대사는 **오른쪽 열만** 쓴다. 왼쪽 열은 폐기됐다.
**코드 식별자는 바꾸지 않는다** — `round`·`deck`·`settle`·`board`·`stardust`는 그대로다.
용어는 UI 문자열의 문제이고, 식별자를 함께 바꾸면 GDD 절 참조와 코드가 어긋난다.

| 폐기 | 확정 | 비고 |
|---|---|---|
| 배치(하다) | **γένεσις**(하다) | 그리스어 '생성'. 도트 글리프 (11-9절) |
| 별자리 패턴 | **황도 12궁** | 2-2절의 대응과 표기를 일치시킨다 |
| 라운드 | **주기**(週期) | |
| 덱 | **공허**(空虛) | 조사 주의 — 덱은 받침, 공허는 모음: `공허를`·`공허는`·`공허가`·`공허로` |

## 3. 별자리 조각 (칩)

### 3-1. 기본 조각 5종

| ID | 이름 | 색 | 문양 | 기본 점수 |
|---|---|---|---|---|
| GAC | Gacrux | 연두 `#7FD44C` | 클로버 ♣ | 10 |
| IMA | Imai | 파랑 `#3F8FE0` | 다이아 ♦ | 10 |
| GIN | Ginan | 빨강 `#E0453F` | 하트 ♥ | 10 |
| MIM | Mimosa | 보라 `#9A4FD4` | X자 ✕ | 10 |
| ACR | Acrux | 검정 `#2B2B38` | 스페이드 ♠ | 10 |

**융합 순서(고정)**: Gacrux → Imai → Ginan → Mimosa → Acrux

### 3-2. 특수 별자리 조각 (₅C₂ = 10종)

두 문양을 반반 합친 칩. 융합 시 **두 문양 모두로 판정**되며, 양쪽 라인에 동시 기여한다.

**표기 규칙**: 좌/우는 **융합 순서(GAC → IMA → GIN → MIM → ACR)** 로 정규화한다.
즉 항상 순서가 앞선 문양이 `left`, 뒤선 문양이 `right`다. 중첩 루프 `i < j`로 10종이 자동 생성된다.

```
GAC&IMA  GAC&GIN  GAC&MIM  GAC&ACR
IMA&GIN  IMA&MIM  IMA&ACR
GIN&MIM  GIN&ACR
MIM&ACR
```

> 좌/우는 **시각적 배치에만** 영향을 준다(왼쪽 절반 색·문양). 융합은 두 문양을 대등하게 처리하므로
> 순서를 정규화해도 게임 로직에 변화가 없다. 초기 설계안 대비 3종의 좌우가 바뀐다
> (MIM&GAC → GAC&MIM, ACR&GAC → GAC&ACR, ACR&IMA → IMA&ACR).

**디자인 규칙**
- 칩 왼쪽 절반 = Something1의 색 / 오른쪽 절반 = Something2의 색
- 중앙 문양 = Something1 문양의 **왼쪽 절반** + Something2 문양의 **오른쪽 절반**을 이어 붙임

**획득**: иєвυℓα 상점에서만. 매 상점마다 10종 중 **랜덤 4종** 진열.

### 3-3. 떠돌이 별자리 조각 (1종, 게임당 1개 한정)

융합 시 인접 4방향 중 **랜덤 3방향**을 선택해, 그 방향에 있는 칩의 문양으로 **전부 판정**된다.

| 인접 칩 수 | 선택 방식 |
|---|---|
| 4개 | 랜덤 3방향 선택 (₄C₃ = 4가지, 각 1/4) |
| 3개 | 3개 전부 강제 선택 |
| 2개 | 2개 전부 강제 선택 |
| 1개 | 1개 강제 선택 |
| 0개 | 판정 없음 (0점) |

- 판정된 문양으로 **점수·라인 판정 모두** 참여한다.
- **중복 문양은 집합으로 합친다.** 선택된 3방향이 Gacrux·Gacrux·Ginan이면 결과는 {Gacrux, Ginan} 2종이다.
  떠돌이는 칸 하나를 차지하므로, 한 칸이 "Gacrux 2개"일 수는 없다. 라인 판정과 모순되지 않기 위한 필연적 규칙이다.
- **인접 칩이 MЦLГЦS 조각이면 두 문양을 모두 얻는다.** MЦLГЦS 조각은 어디서든 두 문양 그 자체이므로 일관되게 처리한다.
  따라서 한 방향에서 2종을 얻을 수 있고, 3방향 전부 MЦLГЦS 조각이면 최대 5종(중복 제거 후)까지 가능하다.

> 🎯 **전술적 함의**: 집합 규칙 때문에 떠돌이는 **같은 문양이 몰린 곳보다 문양 경계에 놓을 때** 강하다.
> 별자리 시스템이 같은 문양 연속을 보상하는 것과 방향이 반대라, γένεσις 판단에 긴장이 생긴다.
- **지급 규칙**: 판매하지 않는다. **иєвυℓα와의 첫 만남에서 1개를 무상 지급**하고, 이후 다시 등장하지 않는다 (13-4절).

## 5. 융합 알고리즘 (핵심)

### 5-1. 의사코드

```
총점 = 0
for 문양 in [GAC, IMA, GIN, MIM, ACR]:          # 고정 순서
    S = 성단 위에서 이 문양으로 판정되는 모든 칩
    if S 비어있음: continue

    발동라인들 = 보유 별자리로 탐색한 maximal 라인 전체

    for 라인 L in 발동라인들:
        라인배율 = Σ( L 조건을 만족시키는 보유 별자리들의 배율 )
        총점 += (L의 칩 수 × 10) × 라인배율

    비라인칩 = S 중 어떤 발동라인에도 속하지 않는 칩
    총점 += 비라인칩 수 × 10 × 1.0

    if 게자리 발동 and 이 문양이 최다 문양:
        총점 += S 전체 수 × 10 × 0.1
```

#### ★ 융합 결과의 분해 구조 (BOOTH-4a 확정, 미해결 #13 해소)

`scoreBoard()`(위 의사코드의 구현, `src/core/scoring.ts`)는 총점 외에 **두 축의 분해**를
함께 돌려준다. 둘 다 위 루프가 이미 계산한 값을 버리지 않고 모아둔 것이며,
**총점 계산식에는 손대지 않는다.**

```ts
interface ScoreResult {
  total:  number                  // 위 의사코드의 '총점'
  lines:  ScoredLine[]            // 발동한 라인 전체
  bySuit: SuitBreakdown[]         // 문양 축 — 점수를 못 낸 문양은 생략
  byCell: CellContribution[]      // 칸 축 — 칩이 놓인 칸 전부, row-major
}

interface CellContribution {
  position:    Position
  lineScore:   number   // 이 칸이 속한 발동라인 전부의 합
  flatScore:   number   // 라인에 안 든 문양마다 ×1.0
  cancerBonus: number   // 문양 전체 보너스 중 이 칸 몫
  total:       number   // 위 셋의 합
}
```

**분해 규칙 3가지 (확정)**

| 항목 | 규칙 | 근거 |
|---|---|---|
| **교차 중복** | 가로·세로 라인에 동시에 든 칩은 **양쪽에서 각각** `10 × 배율`을 받는다. 라인 하나에만 든 칩의 정확히 2배가 된다. **어느 라인이 얼마를 줬는지는 보관하지 않는다** — 필요하면 `lines[].positions`로 역추적한다 | 5-2절 B-4 |
| **반올림** | 칸마다 `Math.round`. `sum` 모드에서는 칸 기여가 전부 정수(`10 × 소수 1자리 배율`)이므로 **Σ byCell.total = total 이 정확히 성립**하며 테스트로 고정했다. `product` 모드는 배율에 소수 2자리가 붙어 이 등식이 깨질 수 있으나, 이는 `bySuit`가 이미 갖는 한계와 같고 Phase 2 비교 전용 모드다 | 미해결 #3 |
| **다문양 칸** | 떠돌이(최대 3문양)·MЦLГЦS 조각(2문양)은 **문양별로 쪼개지 않고 한 칸의 합계로** 담는다. 문양 축이 필요하면 `bySuit`가 그 축이다 | 3-2·3-3절 |

- 칩이 놓인 칸은 **기여가 0이어도 항목이 존재**한다. 인접 칩이 없는 떠돌이가 그 경우다(3-3절).
- 빈 칸은 항목을 만들지 않는다. 빈 성단의 `byCell`은 빈 배열이다.
- 비용: `smart` 정책 200판 몬테카를로 기준 19,375ms → 19,319ms로 **측정 오차 범위**다.
  옵션 플래그로 끄고 켤 필요가 없다.

> **이 분해는 두 기능의 선행 조건이다.**
> ① **DRIFT ORACLE**(8-3절) — 정답 시 "그 턴 **떠돌이 점수** +50%"를 지급하려면
> 떠돌이가 놓인 칸의 기여를 총점에서 분리할 수 있어야 한다.
> ② **P4-B 동반성 A군 12종**(7-2절 A~J 분류) — "칩 기본점수 결정" 지점에 끼어드는
> 훅이므로, 칩 하나가 이번 융합에서 어떤 배율로 몇 번 계산됐는지가 먼저 표현 가능해야 한다.
> `byCell`이 그 표현이다.

#### 발동 연출 — 정수 픽셀 이동 (BOOTH-2b)

문양별 융합이 진행되는 동안 그 단계에서 발동한 별자리 카드가 반응한다. 연출 자체는 유지하되
**방식이 바뀌었다.**

| | 이전 | 현재 |
|---|---|---|
| 움직임 | `scale: 1.08` | `y: [0, -2, 0]`, `ease: [steps(1), steps(1)]` |
| 빛 | `boxShadow 0 0 14px <축색>` | 그대로 |

`scale: 1.08`은 **CLAUDE.md §7의 정수배 규칙 위반**이었다. 카드의 별 도트와 이름·조건·배율
텍스트 전부가 발동 내내 픽셀 경계에 걸쳐 뭉개졌고, 하필 플레이어가 바로 그것을 보고 있는
순간이었다. 2px 도약은 어떤 정수 캔버스 배율에서도 정수 디바이스 픽셀로 떨어진다(11-10절).

> ⚠️ **`steps(1)` 하나로는 안 된다.** 이징 함수를 하나만 주면 키프레임 배열 **전체**에 적용되어
> 첫 키프레임을 유지하다 마지막으로 점프하는데, `[0, -2, 0]`은 양 끝이 모두 0이라 카드가
> 아예 움직이지 않는다. 구간마다 하나씩 `[steps(1), steps(1)]`로 주어야 한다.

#### ★ 융합은 자동으로 진행된다 — 속도 선택도 버튼도 없다 (BOOTH-9b 확정)

**턴 종료를 누르면 그 뒤로 플레이어가 누를 것이 없다.** 융합이 문양별로 걸어가고, 다 걸은 뒤
2초 있다가 다음 턴으로 넘어간다.

| | 이전 | 현재 |
|---|---|---|
| 속도 | `1×` `2×` `즉시` 3택 | **`1×` 고정** (문양당 600ms) |
| 진행 | `건너뛰기` / `다음 턴` 버튼 | **자동** |
| 패널 우상단 | 속도 버튼 + 진행 버튼 | 상태 문구 `융합 중` / `곧 다음 턴` |

**왜 없앴나.** 부스 참여자는 한 런에서 이 패널을 **15번** 만나고(12-1절), 그때마다 속도를 고르고
버튼을 누르는 **결정을 두 번** 했다. 이 화면의 일이 *보는 것*인데 조작을 시킨 것이다.
컨트롤을 치우는 것이 융합을 "플레이어가 조작하는 것"에서 "플레이어에게 일어나는 것"으로 바꾼다.

| 상수 | 값 | 위치 |
|---|--:|---|
| 문양당 진행 | 600ms | `config.ts` — `SUIT_STEP_MS` |
| 융합 종료 후 대기 | 2,000ms | `config.ts` — `SETTLEMENT_HOLD_MS` |

> **왜 밸런스 파일에 애니메이션 상수가 있나.** 이제 이것이 부스의 시간 예산이기 때문이다.
> 넘어가는 데 걸리는 시간을 플레이어가 줄일 수 없으므로 15회 × (걷기 + 대기)는 12-1절 28분에서
> **고정 비용**이다. 참여자가 자리를 얼마나 오래 차지하는지를 정하는 수치는 주기 수가 있는 곳에
> 있어야 한다.
>
> **대기는 걷기가 끝난 시점부터 잰다.** 걷는 길이는 몇 문양이 득점했느냐에 따라 달라지므로
> (5-1절은 0점 문양을 건너뛴다) 시작점부터 재면 짧은 융합에는 긴 꼬리가, 긴 융합에는 거의 없는
> 꼬리가 붙는다.

**★ 모달이 떠 있는 동안 타이머는 돌지 않는다 — 절대 규칙.**
자동 진행의 유일한 위험은 이것이다. 모달은 게임이 플레이어에게 *읽으라고* 내민 것이고, 그 뒤에서
타이머가 돌면 게임이 플레이어 대신 답해 버린다. 판정은 순수 함수 `autoAdvances()`에 있고
(`ui/Settlement.tsx`), 네 가지를 하나씩 세는 테스트가 `tests/settlement.test.ts`에 있다.

| 모달 | 절 | 겹칠 수 있나 |
|---|---|---|
| ORION'S WAGER | 8-2 | 실제로는 불가 — `dismissSettlement`가 만든다 |
| DRIFT ORACLE | 8-3 | 실제로는 불가 — 융합 **전에** 닫힌다 |
| CONSTELLATION LOG | 8-4 | 실제로는 불가 — `dismissSettlement`가 만든다 |
| **ESC 퍼즈 창** | 12-2 ①④ | **가능** — 플레이어가 아무 때나 연다 (12-2-d) |

> 앞의 셋도 목록에 넣는다. 지금 겹치지 않는 것은 전이 순서 덕분이고, 순서가 바뀌면 조용히
> 깨진다 — 넣어 두면 우연이 아니라 규칙이 된다. 모달이 열리면 타이머는 해체되고, 닫히면
> **처음부터 2초**를 다시 센다. 남은 시간을 이어 세지 않는다.
>
> ⚠️ **BOOTH-9c에서 9b의 `? 요약`·`중도 리셋 확인` 두 행이 `ESC 퍼즈 창` 한 행이 됐다.**
> 둘 다 퍼즈 창의 페이지가 되었으므로 동시에 참일 수 없고, 필드도 `pauseOpen` 하나다.
>
> ★ **문양별 걷기도 함께 멈춘다.** 퍼즈 창은 불투명하므로(11-10절) 뒤에서 걷는 융합은 아무도
> 보지 못한 채 끝난다. 대기 타이머만 멈추면 "설명을 빼앗지 않는다"는 이 규칙의 목적이 절반만
> 지켜진다.

**★ 애니메이션을 꺼도 2초 대기는 그대로다 (BOOTH-9c).** 12-2-d의 스위치는 `SUIT_STEP_MS`를
사실상 0으로 만들지만 `SETTLEMENT_HOLD_MS`는 건드리지 않는다. 대기는 *연출*이 아니라 **읽는
시간**이고, 걷기가 사라지면 화면에 숫자가 머무는 시간은 최대 3초 짧아진다 — 여기서 대기까지
줄이면 정산이 스쳐 지나간다. 줄여야 할 이유는 시간 예산인데, 애니메이션을 끄는 것은 이미 걷기
쪽에서 예산을 돌려준다.

> ⚠️ **`ms = 0` 경로에는 버그가 있었다 (BOOTH-9c에서 발견·수정).** 걷기를 `onIndex(steps.length)`로
> 한 번에 끝내던 분기가 정산을 `융합 중`에서 멈춰 세우고 턴을 영원히 넘기지 않았다 — 자식
> 이펙트가 부모보다 먼저 커밋되므로 `Game.tsx`의 인덱스 초기화가 그 뒤에 덮어썼고, 그 시점에
> 이펙트의 의존성은 하나도 바뀌지 않아 다시 돌지 않았다. **`prefers-reduced-motion`이 켜진 부스
> 노트북은 첫 정산에서 멈췄을 것이다.** 지금은 0ms짜리 타이머로 문양당 한 걸음씩 걷는다
> (5문양 ≈ 20ms, 한 프레임). `npm run shot`이 3주기 전체를 애니메이션 off로 돌려 재발을 잡는다.

**마지막 턴.** 5턴째에는 넘어갈 다음 턴이 없다. 특례는 두지 않았다 — `endTurn`이 5턴째에
`phase`를 `roundEnd`로 놓고(4-1절) `dismissSettlement`가 그 위상을 읽으므로, **턴을 넘기는 호출과
주기를 끝내는 호출이 같은 호출**이다. 무엇이 다음인지는 core가 정한다(CLAUDE.md §5).

### 5-2. 배율 규칙 (확정)

| 도형 중복 | **꼭짓점이 다르면 칸을 공유해도 각각 별개 라인** (ㅅ자·ㅗ자 포함) | 신규 확정 |
| 대각선 정의 | ↘·↗ 양방향 + 오프셋 대각선 전부 인정 | B-5 |

> 🔧 **튜닝 포인트**: 스택 방식(단순합 vs 곱연산 vs `1.0 + Σ(배율-1.0)`)은
> `src/core/config.ts`의 상수로 분리해 몬테카를로로 비교 검증할 것.

#### ★ 동반성 배율은 별자리와 다른 방식으로 합성한다 (P4-B-0 확정)

**동반성 배율의 합성은 델타 합 `1.0 + Σ(m − 1.0)` 이다.** 위 표의 별자리 스택 방식
(**순진 합** `Σm`)과 **다른 연산**이며, 두 방식이 한 융합 안에 공존한다.

**이유: 동반성에는 1.0 미만의 배율이 존재한다.**

| 동반성 | 배율 | 7-2절 |
|---|---|---|
| #4 맥동 주계열성 | **×0.7** → ×1.8 교대 | 주계열성 |
| #16 불안정 성운 | **×0.5** ~ ×2.0 무작위 | 성운 |

순진 합으로 계산하면 이 둘이 **페널티가 아니라 보너스로 뒤집힌다.**
×0.7과 ×1.5를 함께 가진 경우:

```
순진 합   : 0.7 + 1.5 = 2.2   ← ×0.7이 점수를 22% 올린다 (설계 의도와 반대)
델타 합   : 1.0 + (0.7−1.0) + (1.5−1.0) = 1.2   ← ×0.7이 제 몫만큼 깎는다
```

별자리 배율은 전부 1.0 초과(최소 게자리 ×1.1)라 이 문제가 없다.
**미해결 #3의 `sum` 확정은 별자리에 한한 결정이며, 이 절이 그것을 변경하지 않는다.**

> 두 방식이 섞이는 지점의 정확한 순서는 **7-1-b절의 6단계**가 정의한다.

```

점수     = (5칸 × 10점) × 5.5 = 275점
```

## 8. 확률·통계 학습 레이어 (B안)

### 8-1. STAR-CHART — 실시간 공허 확률 패널

BLACK-HOLE 옆 **상시 표시**.

| 표시 | 내용 |
|---|---|
| 문양별 잔여 장수 | Ginan 7 / 50 |
| 잔여 비율 | 14% |
| 다음 8장에 1장 이상 나올 확률 | `1 − C(43,8)/C(50,8)` = 73.0% |

드로우마다 막대 그래프가 실시간 변동 → **비복원추출**(Ⅲ-5 모집단과 표본)을 시각적으로 체감.

> ⚠️ **정정 1 (P5)**: 이 표의 확률은 오래 **78.4%로 적혀 있었으나 계산이 틀렸다.**
> 당시 예시(40장 공허)로 `C(33,8)/C(40,8) = 13,884,156 / 76,904,685 = 0.18052`이므로
> `1 − 0.18052 = 0.8195`가 맞았다. 식은 그대로 두고 값만 고쳤다.
>
> ⚠️ **정정 2 (BOOTH-3b)**: 예시 자체가 **40장 공허 기준이었다.** 초기 공허는 4-2절(C-7)이
> 정한 대로 **50장**이므로, 게임에 없는 공허 크기로 패널을 설명하고 있었다. 같은 "Ginan 7장
> 남음" 상황을 50장 기준으로 다시 계산해 표를 고쳤다 —
> `C(43,8)/C(50,8) = 145,008,513 / 536,878,650 = 0.27010`이므로 `1 − 0.27010 = 0.7299`다.
> **식의 형태는 바뀌지 않았다.** `tests/probability.test.ts`가 이 예시를 BigInt 정확 조합과
> 대조하므로 다시 어긋날 수 없다.

#### 구현 (P5)

| 항목 | 위치 |
|---|---|
| 확률 계산 (수학적) | `src/core/deck.ts` — `chanceOfDrawing(deckSize, ofSuit, handSize)` |
| 문양 5종 일괄 | `src/core/deck.ts` — `drawChances(deck, handSize)` |
| 관측 도수 (통계적) | `src/core/deck.ts` — `observedChances(drawHistory)` |
| 잔여 장수 집계 | `src/core/deck.ts` — `countDeck(deck)` |
| 화면 | `src/ui/Shop.tsx` — `DeckPanel` (좌표는 `SHOP_LAYOUT.deck`, 11-10절) |
| 테스트 | `tests/probability.test.ts` |

**공식** — n = 공허 잔여, k = 그 문양 잔여, h = 손패 장수일 때

```
P(적어도 1장) = 1 − C(n−k, h) / C(n, h)
              = 1 − ∏ (n−k−i) / (n−i)      (i = 0 … h−1)
```

여사건(Ⅱ-2)으로 계산한다. "적어도 1장"은 경우를 전부 더해야 하지만 "한 장도 없음"은 몫 하나다.

구현은 **팩토리얼을 만들지 않고 곱을 누적한다.** `C(50,8)`이 이미 5.4×10⁸이고 60!은 배정밀도
범위를 넘으므로, 분자·분모를 따로 세우면 나눗셈 전에 답이 `Infinity ÷ Infinity`로 사라진다.
누적곱은 각 인수가 [0,1]이라 값이 확률 범위를 벗어날 수 없다.

경계 처리 — `k = 0`이면 0, `n − k < h`이면 1(다른 문양만으로는 손패를 채울 수 없으므로 반드시
섞인다). **0 판정을 먼저 한다**: 공허가 손패보다 작을 때 없는 문양을 확실하다고 보고하면 안 된다.

#### ★ 수학적 확률과 통계적 확률을 나란히 놓는다

패널은 문양마다 **두 개의 %**를 보여준다. 이 대비가 STAR-CHART의 존재 이유다.

| 열 | 뜻 | 출처 |
|---|---|---|
| **계산** | 남은 장수로 구한 값 (위 공식) | `drawChances` |
| **실제** | 지금까지 받은 손패 중 그 문양이 들어 있던 비율 | `observedChances` |

두 열은 **같은 사건**을 재야 한다 — "손패에 그 문양이 1장 이상". 그래서 양쪽 모두 `countDeck`으로
세고, MЦLГЦS 조각은 양쪽에서 두 문양 모두에 계상된다(3-2절). 사건 정의가 어긋나면 붙어 있는 두
숫자가 서로 다른 질문의 답이 된다.

실측 예 — 주기 1 종료 시점, 5문양이 모두 10/51이라 **계산은 다섯 줄 모두 85%**인데
**실제는 100 / 80 / 100 / 60 / 100%**로 흩어진다. 손패 5판이라는 작은 표본에서 계산값과 관측값이
갈라지는 것을 학생이 설명 없이 바로 본다.

> ⚠️ **수렴을 주장하지 않는다.** 공허는 주기 안에서 줄고 주기마다 다시 쌓이므로(4-2절)
> 관측이 누적되는 동안 계산값 자체가 움직인다. 문구는 1-4절 ②에 따라 **표본추출(Ⅲ-5)** 맥락으로만
> 쓰고, 1-4절 ①이 Ⅲ-3으로 배정한 **`큰수의법칙`은 언급하지 않는다.**

#### ★ h는 상수가 아니라 설정이다

`h`를 8로 박지 않는다. `src/core/config.ts`의 `HAND_SIZE`에서 읽고, `chanceOfDrawing`은 h를
인자로 받는다. **7-2절 동반성 `표본추출 원시별`(epic)이 매 턴 손패를 8장 → 10장으로 바꾸기**
때문이다. 그 동반성을 보유한 상태에서 패널이 계속 8장 기준으로 말하면, 플레이어가 실제로
받게 될 손패가 아닌 것의 확률을 보여주게 된다. 동반성 효과가 켜지는 P4-B-x 시점에는
`DeckPanel` 호출부가 `HAND_SIZE` 대신 **유효 손패 크기**를 넘기도록 바꾸면 되고,
`src/core/`는 손댈 필요가 없다.

#### ⚠️ 스크림이 STAR-CHART를 덮는 결함과 그 해소 (BOOTH-6c 확정)

**WAGER 모달의 스크림(85% 불투명)이 게임 화면 STAR-CHART를 가린다.** 학습 장치 둘이 서로를
무력화하고 있었다 — 학생은 확률 문항에 답하려면 남은 장수를 봐야 하는데, 답하는 시점에 그 값이
화면에 없다. **문항 문구는 장수를 담지 않는다**(해설에만 있고 해설은 답한 뒤에 나온다).
시간 문제가 아니라 **문항이 풀 수 없는 문제가 되는** 결함이다.

**검토한 네 안**

| 안 | 판정 | 이유 |
|---|---|---|
| A. 스크림에 STAR-CHART 영역만 구멍 | ❌ **불가** | 스크림이 아니라 **패널 본체**가 가린다. 패널은 (200,135,720,360)이고 STAR-CHART는 (588,244,108,380) — y 244~495에서 겹쳐 패널이 **380px 중 251px(66%)** 를 덮는다. 패널이 평면 중앙에 있는 한(11-10절) 폭을 56px 아래로 줄이지 않으면 겹침이 사라지지 않는다 |
| B. **패널 안에 관련 문양의 남은 장수를 표시** | ✅ **채택** | 학생이 이미 보고 있는 곳에 값을 둔다. 확률을 싣지 않으므로 정답이 노출되지 않는다 |
| C. 스크림 불투명도 인하 | ❌ **무효** | 0%로 해도 패널 본체가 66%를 덮는다. 모달 가독성만 잃는다 |
| D. 패널을 비중심으로 옮겨 STAR-CHART를 노출 | ❌ **기각** | 노출되는 것에 **확률 % 열이 포함**된다. comparison 문항은 두 백분율을 읽기만 하면 풀린다. 막으려면 문항이 뜬 동안 % 열을 숨겨야 하는데, 그것은 8-1절의 **상시 표시**를 깨는 것이다 |

**채택안 — `WagerBasis`: 공허 장수 + 문항이 지명한 문양의 장수**

```ts
interface WagerBasis {
  deckSize: number
  counts: { suit: SuitId; count: number }[]   // 문항이 부르는 순서대로
}
```

**정답 노출을 막은 방법은 "확률을 넘기지 않는 것"이다.** 안전장치가 아니라 **타입에 확률을 담을
자리가 없다** — `generateWager`는 `chance`를 손에 들고 있으면서 의도적으로 쓰지 않는다.

| 티어 | 장수만으로 정답이 읽히는가 | 남는 학습 |
|---|---|---|
| `comparison` | 장수 대소 ⟺ 확률 대소(단조). **한 단계 추론이 남는다** | Ⅱ-1 "장수가 많으면 나올 가능성이 크다" — 이게 이 티어의 학습 목표 그 자체다 |
| `complement` | ❌ 안 읽힌다. `1 − chanceOfDrawing(n,k,8)`을 기준값과 비교해야 한다 | Ⅱ-2 여사건 |
| `conditional` | 부분적으로 읽힌다(장수 대소 ≈ 몫의 절반 초과). **부스판 3주기는 이 티어를 만나지 않는다** | Ⅱ-3 조건부 |

##### ★ 재판정 — STAR-CHART가 상단으로 갔어도 결론은 그대로다 (BOOTH-9b)

BOOTH-9b가 STAR-CHART를 (588,244)에서 상단 (656,8)로 옮겼다. 위 D안이 기각된 근거가
"패널 본체가 66%를 덮는다"였으므로, 패널이 더 이상 덮지 않게 된 지금 **% 열이 노출되어
comparison 문항이 읽기만 하면 풀리는가**를 다시 물어야 한다.

**답: 노출되지 않는다.** 스크림은 패널이 아니라 **평면 전체**(0,0,1120,630 · z=50)를 덮고,
STAR-CHART는 z를 갖지 않으므로 어디에 있든 그 아래다. 브라우저에서 실측했다 —
스크림이 뜬 상태에서 STAR-CHART 중앙의 최상위 엘리먼트는 `rgba(10,10,18,0.847)` 스크림이다.

**투과 후 명도 대비** (WCAG 본문 기준 4.5:1 · 큰 글씨 3:1):

| 잉크 | 가림 없음 | 스크림 통과 |
|---|--:|--:|
| GAC | 10.06 | **1.29** |
| IMA | 5.47 | **1.17** |
| GIN | 4.48 | **1.13** |
| MIM | 3.91 | **1.12** |
| ACR | 9.90 | **1.29** |
| starWhite | 16.45 | **1.44** |

전부 1.08~1.44:1로, 기준의 4분의 1에 못 미친다. **% 열은 읽히지 않는다.**
따라서 위 B안(`WagerBasis`)은 여전히 필요하고, D안의 기각 사유도 여전히 유효하다 —
옮겼기 때문에 노출된 것이 아니라, **스크림이 평면 전체를 덮으므로 위치와 무관**했던 것이다.

> 결론적으로 이 절은 손댈 것이 없다. 다만 "패널 본체가 덮는다"는 서술은 이제 세로형 시절의
> 사정이다 — 지금 덮는 것은 스크림이고, 그것으로 충분하다.

> **% 열을 넘기지 않는 것이 이 설계의 전부다.** 8-2절이 이미 같은 전제에 서 있다 —
> `WAGER_MIN_GAP` 절이 "남은 장수가 같다는 것은 STAR-CHART에서 그대로 읽히고, '같다'가 곧
> 답이기 때문이다"라고 적고 있으므로, **장수가 답하는 시점에 읽히는 것은 원래 설계된 바**다.
> 결함은 스크림이 그것을 빼앗은 것이었고, 확률까지 함께 주는 것은 설계에 없던 일이다.
>
> 표시는 `남은 장수` 라벨 + `공허 N장` + 문양별 `16px 문양 기호 + 전명 + N장`이다. 문양 기호를
> 함께 둔 이유는 성단의 칩과 이어 주기 위해서다(아래 남은 간극).

**오라클(8-3절)·리포트(8-4절) 표는 코드만 유지한다.** 두 화면은 전명을 **한 번도 쓰지 않는다** —
> 오라클 문항·해설은 점수·확률·기댓값만 말하고, 리포트 본문도 별 이름을 부르지 않는다. 즉 그
> 두 곳에는 대응시킬 짝이 없어 불일치가 성립하지 않는다. 오라클 표에 전명을 넣으면 판정 문양
> 열이 최대 5문양이라 720px 폭을 넘긴다(같은 절의 최장 행 검사).
>
> ⚠️ **남은 간극 하나 — 성단은 기호, 표는 코드다.** 학생은 성단의 칩을 **문양 기호**로
> 식별하는데 오라클 표와 리포트는 코드로 부른다. 이번에 손대지 않았다. 기호↔코드는 별개
> 문제이며 STAR-CHART가 둘을 나란히 보여주는 것이 현재의 유일한 연결이다.

### 8-2. ORION'S WAGER — 예측 베팅 ★핵심

- **시점**: 매 턴 드로우 **직전**
- **형식**: `YES` / `NO` / `기권` 3지선다
- **보상**: 적중 시 St4RDu3t +2, 오답 시 없음 (**패널티 없음**)
- **강제성**: 선택제. **단, 게임 최초 3회는 튜토리얼로 강제** (확정)

**난이도 곡선**

| 주기 | 문제 유형 | 예시 | 교과 |
|---|---|---|---|
| 1–2 | 단순 비교 | "Ginan과 Acrux 중 어느 쪽이 더 많이 나올까?" | Ⅱ-1 수학적 확률 |
| 3–5 | 여사건 활용 | "이번 8장에 Ginan이 **1장도 안 나올** 확률이 절반을 넘을까?" | Ⅱ-2 여사건 |
| 6–8 | 조건부 | "**지금 공허가 이 상태일 때**, Ginan이 Acrux보다 많이 나올까?" | Ⅱ-3 조건부확률 |

> ⚠️ **문항 작성 절대 규칙 (교과서 지도상의 유의점)**
> 조건부확률 문항은 **"이미 ~했으니 이제"** 같은 **시간적 순서·인과관계 표현을 쓰지 않는다.**
> 반드시 **"지금 공허가 이러할 때"** 처럼 **조건 상태를 제시하는** 형태로만 작성한다.
> 교과서가 명시적으로 경고한 오개념이므로, 위반 시 교육적으로 역효과가 난다.

**오답 시 즉시 해설 팝업** — 왜 그 확률인지 1~2문장으로.

#### 구현 (BOOTH-3a)

| 항목 | 위치 |
|---|---|
| 문항 생성 | `src/core/wager.ts` — `generateWager(deck, round, rng, handSize?)` |
| 주기 → 티어 | `src/core/wager.ts` — `wagerTierFor(round)` (`WAGER_TIER_BY_ROUND` 조회, 표 밖 주기는 양 끝으로 클램프) |
| 확률 계산 | `src/core/deck.ts` — `chanceOfDrawing` / `drawChances` 재사용 (8-1절) |
| 최소 격차 · 여사건 기준값 | `src/core/config.ts` — `WAGER_MIN_GAP`, `WAGER_COMPLEMENT_THRESHOLDS` |
| 테스트 | `tests/wager.test.ts` |

**명제 은행은 없다.** 문항은 그 시점의 공허에서 만들고 정답은 같은 공허 수치로 계산한다. 상점에서
공허를 고치거나 주기가 공허를 깎으면 같은 티어라도 다른 문항·다른 정답이 나온다. `handSize`는
8-1절과 같은 이유로 인자다 — `표본추출 원시별`이 손패를 10장으로 바꾸면 문항도 따라가야 한다.

**티어별 명제 유형** — 티어마다 형태가 둘 이상이고(비교는 셋, 여사건은 기준값이 다섯), 그 시점
공허에서 만들 수 있는 명제를 전부 만든 뒤 하나를 고른다.

| 티어 | 주기 | 명제 형태 | 실제로 묻는 값 | 후보 수 |
|---|---|---|---|---|
| `comparison` | 1–2 | "A가 1장 이상 나올 가능성이 B보다 **크거나 같을까**?" | `drawChances`의 두 값 대소 | 20 |
| 〃 | 〃 | "A의 그 가능성과 B의 그것이 **정확히 같을까**?" | 같은 두 값의 일치 | 10 |
| 〃 | 〃 | 〃 "**서로 다를까**?" | 같은 두 값의 불일치 | 10 |
| `complement` | 3–5 | "A가 **1장도 안 나올** 확률이 *t* 를 넘을까?" | `1 − drawChances[A]` 와 기준값 *t* | 5문양 × 5기준 = 25 |
| `conditional` | 6–8 | "뽑은 1장이 A나 B라는 조건에서 그것이 A일 가능성이 절반보다 클까?" | `chanceOfDrawing(A∪B 장수, A, 1)` = A/(A∪B) 와 1/2 | 20 |
| 〃 | 〃 | 〃 "정확히 절반일까?" | 같은 값의 1/2 일치 | 20 |

조건부는 **조건이 표본공간을 `A∪B`로 좁히는** 형태다. MЦLГЦS 조각은 두 문양을 다 가지므로
`countDeck`의 문양별 합이 아니라 **합집합 장수**로 세야 한다(`countEither`). 한 장이 두 번
세어지면 조건부 확률 자체가 틀린다.

**최소 격차** — `WAGER_MIN_GAP = 0.05`. 비교하는 두 값의 차가 이보다 작으면 출제하지 않는다.
40~50장 공허에서 칩 1장 차이는 등장 확률을 0.03쯤 움직이는데, 그 정도는 학생이 계산을 정확히
해도 판단할 수 없다. 0.05는 대략 **2장 차이**다. **두 값이 정확히 같은 경우는 예외로 출제한다** —
남은 장수가 같다는 것은 STAR-CHART에서 그대로 읽히고, "같다"가 곧 답이기 때문이다.

**재시도 상한은 두지 않는다.** 후보가 티어당 25~40개뿐이라 전수를 만들어 거르는 편이 싸고,
재시도 방식은 유효한 명제가 남아 있는데도 상한에 걸려 포기할 수 있다. 유효 후보가 하나도
없으면 격차가 가장 큰 후보를 출제한다 — 실제 게임의 공허에서는 발생하지 않는다(미γένεσις 칩이 매 턴
공허로 돌아오므로(4-2절) 문항 생성 시점의 공허는 34장 아래로 내려가지 않는다).

**정답 쏠림 방지** — 시드가 먼저 YES/NO 중 원하는 쪽을 뽑고, 그 답이 되는 명제를 후보에서
고른다. 정답을 조작하는 것이 아니라 **어느 명제를 물을지**를 고르는 것이다. 주기 첫 턴처럼
공허가 균일한 상태에서는 비교 명제의 답이 한쪽으로 고정되므로(모든 문양이 같은 값이라
"크거나 같다"도 "정확히 같다"도 참이 된다), 그 상태에서 NO가 되는 **"서로 다를까"** 형태를
함께 두어 양쪽 답이 모두 성립하게 했다. 여사건 기준값에 `0.05`가 들어 있는 것도 같은 이유다 —
균일한 50장 공허의 "1장도 안 나올" 확률 0.143은 기준 0.1과의 차가 최소 격차에 못 미쳐 탈락하고,
남은 기준값은 전부 NO가 된다. 실측(마모량이 서로 다른 공허 2,000개): comparison 48.0% ·
complement 48.0% · conditional 48.0%가 YES, 균일한 50장 공허만 모으면 세 티어 모두 50.2%.

> ⚠️ **비교 명제는 "클까"가 아니라 "크거나 같을까"다 (BOOTH-3b 개정).** 두 값이 같을 때
> "클까"의 답은 NO가 맞지만, **"크다"의 반대를 "작다"로 읽는 것은 흔한 오개념**이라 같은
> 이해 수준의 학생이 YES/NO로 갈렸다. 학습 장치가 오개념을 교정하지 못하고 언어로 학생을
> 가르는 상태였으므로, 등호를 문장 안에 넣어 무엇을 묻는지 분명히 했다. 같은 논리가
> 조건부의 "절반보다 클까"에도 적용될 수 있으나, 조건부는 균일한 공허에서 "정확히 절반일까"가
> 참이 되어 양쪽 답이 이미 성립하므로 이번에는 손대지 않았다.

**금지 표현 검사** — 1-4절 ③의 시간·인과 표현은 `tests/wager.test.ts`가 금지어 목록으로 막는다.
`이미 · 이제 · 다음엔 · 그다음 · 뒤라서 · 뒤에 · 뒤이어 · 먼저 · 나중 · 방금 · 직전 · 직후 · 이후 ·
이전 · 했으니 · 하고 나서 · 그러고 · 순서대로 · 한 다음 · 때문에`와 기호 `P(` · `|`를, 티어별
공허 300개에서 생성한 **문항과 해설 전문**에서 찾는다. 기호는 중학생 대상이라 함께 막는다.

**해설**은 `WagerQuestion.explanation`에 담는다. 실제 수치로 근거를 대고, YES/NO 중 **틀린
쪽을 고른 학생이 무엇을 착각했는지**를 한 문장으로 짚는다. 해설도 같은 금지 표현 검사를 받는다.

#### 출제 · 채점 배선 (BOOTH-3b)

| 항목 | 위치 |
|---|---|
| 출제 | `src/core/game.ts` — `askWager(game)` (`pendingWager`에 문항을 올린다) |
| 강제 구간 판정 | `src/core/game.ts` — `wagerIsForced(game)` (`wagerHistory.length < FORCED_WAGER_COUNT`) |
| 채점 · 보상 · 기록 | `src/core/game.ts` — `resolveWager(game, choice)` |
| 시뮬레이터 경로 | `src/core/game.ts` — `awardWager(game, correct)` (문항 없이 보상만) |
| 화면 | `src/ui/Wager.tsx` — `WagerPanel` (좌표는 `LAYOUT.wager`, 11-10절) |
| 스토어 | `src/store/gameStore.ts` — `answerWager` / `dismissWager` |

**시점과 빈도** — 이 절 첫머리가 정한 그대로 **매 턴 드로우 직전 1회**다. 빈도를 따로 정하지
않는다. 배선도 그 순서를 강제한다: 손패를 만드는 `drawHand`는 `resolveWager`가 문항을
치운 뒤에만 호출되고, 주기 시작·융합 종료·상점 퇴장 세 지점이 모두 `askWager`로 들어간다.
따라서 **답하지 않으면 손패가 없다.**

**강제 구간** — 최초 `FORCED_WAGER_COUNT`(3)회는 `기권` 버튼을 비활성화하고 이유를 한 줄로
알린다. 화면이 막는 것에 더해 **core가 거부한다** — 강제 구간의 `abstain`은 게임 상태를 그대로
돌려주며 기록도 보상도 남지 않는다. 무엇이 합법인지는 규칙이고 규칙은 UI에 두지 않는다
(CLAUDE.md §5).

**기권** — 보상도 벌칙도 없다. 기록에는 남으므로 8-4절 리포트에서 "답하지 않음"으로 세어진다.

**해설 표시** — 답한 즉시 같은 상자에서 버튼이 해설로 바뀐다. 문항은 자리를 지키므로 학생이
문장과 근거를 나란히 읽는다. 정답이면 `정답`과 획득 St4RDu3t를, 틀리면 `오답`과 **정답이
무엇이었는지**를 함께 보여준다.

**남은 장수 표시** — 문항 아래에 공허 장수와 지명된 문양의 장수를 함께 인쇄한다. **확률은 싣지
않는다.** 결함 전말과 대안 비교는 8-1절 「스크림이 STAR-CHART를 덮는 결함」.

#### ★ 정답 시 해설 생략 (BOOTH-6b 확정)

**오답·기권에만 해설 전문을 띄운다. 단, 강제 구간 3회는 정답이어도 띄운다.**

이 절이 원래 규정한 것은 "**오답 시** 즉시 해설 팝업"이다. 정답에도 띄우는 것은 구현이 더한
것이었고, BOOTH-6a가 그 대가를 실측했다 — WAGER가 학생 소요 32.4분의 **44%**(14.1분)를 썼다.
축소 후는 27.6분의 **31%**(8.5분)다. 재산정 전말은 12-1절.

| | 화면 |
|---|---|
| 오답 | `오답` + 정답이 무엇이었는지 + **해설 전문** |
| 기권 | `기권` + **해설 전문** (기록상 `correct: false`) |
| 정답 · 강제 구간 3회 안 | `정답` + St4RDu3t + **해설 전문** |
| 정답 · 강제 구간 이후 | `정답` + St4RDu3t **만**. 곧 `계속` |

판정은 `src/ui/Wager.tsx`의 `showsExplanation(record, answered)`이며 `answered`는 core가
기록한 문항 수다. **경계가 `<` 아니라 `<=`인 이유**: 해설이 화면에 있을 때 core는 그 문항을
이미 기록했으므로, 방금 답한 것이 `answered`번째다. `wagerIsForced`를 그대로 쓰면 3번째
강제 문항이 해설 없이 지나간다.

> **오라클(8-3절)에는 적용하지 않는다.** 근거 넷: ① 절약이 1런 0.8분(전체의 2.5%)뿐이다
> ② 오라클 선택지는 전부 정수로 제시되어 계산 없이 정답이 눈에 띄지 않게 설계됐으므로
> (8-3절), 정답이 우연일 확률이 2지선다 WAGER보다 낮고 해설은 그 계산을 확인해 준다
> ③ 표는 정답 후에도 화면에 남는다 — 해설만 없애면 표가 이유 없이 남는 화면이 된다
> ④ 기댓값은 가장 낯선 개념인데 노출이 1런 3.4회뿐이다. WAGER는 15회이므로 한 번 생략해도
> 다음 기회가 있으나 오라클은 없다.

#### ★ 해설 길이 — 2요소 규정 (BOOTH-6b 확정)

**해설은 [계산 근거] + [오답 교정] 두 요소이고, 마지막 문장은 항상 `YES/NO를 고르면 …`이다.**

| | 남긴 것 | 버린 것 |
|---|---|---|
| 근거 | 비교 대상의 **장수**(학생이 검산할 수 있는 유일한 값) · 계산된 **확률** | 장수를 독립 문장으로 다시 진술하는 것 |
| 교정 | 어떤 착각인지 짚는 한 문장 | 정성적 부연 (`…그만큼 많다`) |
| 반복 | — | 문항이 이미 말한 것 (`8장 안에`, `여사건이다`) |

**장수와 확률을 문양별로 묶어 제시한다.** `Gacrux 10장(78%), Ginan 12장(84.2%)` — Ⅱ-1의
주장이 "장수가 많으면 확률이 크다"이므로, 두 계열을 따로 나열해 학생이 순서를 대조하게 하는
것보다 짝지어 붙이는 편이 한눈에 읽히고 **동시에 더 짧다.**

**조건부(6~8주기)에서는 공허 전체 장수를 근거에서 뺐다.** 조건이 그것을 계산에서 제거했기
때문이다(`share = count[a] / union`). 공허 장수는 **첫 번째 교정 문장**에만 남는다 — 조건을
무시하는 착각이 바로 그 값을 쓰는 것이므로 거기가 제자리다.

**실측** (`tests/wager.test.ts`와 같은 300공허 표본):

| 티어 | 주기 | 해설 평균 | p90 | 최대 | 문항+해설 평균 |
|---|---|--:|--:|--:|--:|
| `comparison` | 1–2 | **74.7자** | 77 | 79 | 143.4자 |
| `complement` | 3–5 | **77.9자** | 82 | 84 | 129.4자 |
| `conditional` | 6–8 | **88.7자** | 96 | 101 | 169.7자 |
| **부스판 가중(2:1)** | 1–3 | **75.8자** | 79 | 84 | **138.8자** |

축소 전은 해설 평균 **138.8자** / 문항+해설 **201.9자**였다(BOOTH-6a 실측, 이 절의 옛 각주
"203자"를 재현). 해설은 **45% 줄었다.**

조건부만 88.7자로 긴 것은 조건이 남긴 범위 장수라는 셋째 수치를 실어야 하기 때문이고,
**부스판 3주기는 조건부를 만나지 않는다**(`WAGER_TIER_BY_ROUND`가 1–3을 comparison ·
comparison · complement로 배정). 상한은 티어별로 `tests/wager.test.ts`가 지킨다 —
조건부 110자, 나머지 90자.

> ⚠️ **1-4절 ③ 금지 표현 검사는 축소 후에도 전수 통과한다.** 티어별 공허 300개의 문항·해설
> 전문에서 금지어 22개와 기호 `P(`·`|`를 찾는 검사, 그리고 마지막 문장이 `YES/NO를 고르면`으로
> 시작하는지 검사하는 항목이 함께 걸려 있다.

> **처리량 재산정은 이 축소를 반영해 12-1절에서 했다** (BOOTH-6b). WAGER 15문항이
> 3,030자 → **1,627자**로 줄었다.

### 8-3. DRIFT ORACLE — 기댓값 계산

떠돌이 조각 γένεσις 후 융합 **직전**, 떠돌이가 읽을 수 있는 경우를 표로 전부 공개한다.
경우의 수는 인접 칩 수가 정한다 — **인접 4개일 때만 ₄C₃ = 4가지**이고, 3개 이하는
3-3절의 강제 선택이라 1가지다(아래 「인접 칩 수별 동작」). 다음은 인접 4개의 예다.

| 선택된 3방향 | 판정 문양 | 점수 | 확률 |
|---|---|---|---|
| 상·하·좌 | ACR, MIM, GIN | 84 | 1/4 |
| 상·하·우 | ACR, MIM, GAC | 96 | 1/4 |
| 상·좌·우 | ACR, GIN, GAC | 72 | 1/4 |
| 하·좌·우 | MIM, GIN, GAC | 68 | 1/4 |

→ **"이 조각의 기댓값은?"** 3지선다 → 정답 시 그 턴 떠돌이 점수 **+50%**

#### 인접 칩 수별 동작 (3-3절과의 정합)

위 표는 **인접 칩이 4개일 때**만이다. 3-3절은 인접 칩이 3개 이하면 **강제 선택**이라고
규정한다 — 고를 것이 없으므로 경우의 수가 하나다.

| 인접 칩 수 | 경우의 수 | 각 확률 | 화면 |
|---|---|---|---|
| 4 | ₄C₃ = **4** | 1/4 | 위 표 그대로 |
| 3 | **1** (셋 다 선택) | 1 | 판정이 하나로 정해짐 |
| 2 | **1** | 1 | 〃 |
| 1 | **1** | 1 | 〃 |
| 0 | **1** (판정 문양 없음) | 1 | 〃 |

> ⚠️ **인접 칩끼리 문양이 겹치면 서로 다른 3방향 조합이 같은 문양 집합·같은 점수를 낸다.**
> 3-3절의 집합 병합 규칙 때문이다. 표는 **방향 조합마다 한 행**이므로 그때도 4행이고,
> 값이 중복될 뿐이다. 각 행의 확률은 그대로 1/4이며 기댓값도 달라지지 않는다.
> 행을 점수별로 합치지 않는 이유는 표본공간이 **3방향의 선택**이라는 것을 학생이 보아야
> 하기 때문이다 — 위 예시 표의 형식을 그대로 유지한다.

#### ★ 경우의 수가 1가지일 때도 출제한다 (BOOTH-4b 확정)

**P5로 미뤄둔 결정을 여기서 내린다. 출제한다.** 근거 둘:

1. **확률 1인 사건도 기댓값 계산의 정당한 사례다.** 점수에 확률을 곱해 더하는 절차는
   같고, 더할 항이 하나일 뿐이다. 오히려 "확률 1"을 다루어 본 경험이 된다.
2. **강제 선택이 오히려 흔하다.** 부스판 greedy 12판(3주기 × 5턴, 170턴)에서 오라클이
   45번 떴고 그 중 **32번(71%)이 경우의 수 1가지**였다. 여기서 침묵하면 장치가 뜨는
   판이 10/12 → 5/12로 줄고, 학습 기회의 7할이 사라진다.

**다만 4지선다와 같은 얼굴로 내지 않는다.** 문항 문구가 다르다.

| | 인접 4개 (₄C₃ = 4) | 인접 1~3개 (강제) |
|---|---|---|
| 문항 | "…기댓값에 **가장 가까운 값**은?" | "인접한 칩이 N개뿐이라 방향을 고를 여지가 없다. **이 판정 하나가 확률 1로 일어난다.** …기댓값은?" |
| 표 확률 열 | `1/4` | `1` |
| 해설 | 가중합을 쓰고, 최댓값·최솟값이 기댓값이 아님을 짚는다 | **경우가 하나뿐이므로 그 점수가 곧 기댓값**임을 말하고, 그래도 계산 절차는 같음을 보인다 |

> **인접 칩이 0개면 출제하지 않는다.** 3-3절이 판정 없음(0점)으로 규정하므로 확률변수 자체가
> 없고, 어떤 답도 0이 되는 문항이 된다. 이때 `askOracle`은 게임을 그대로 돌려준다.

#### 구현 (BOOTH-4b)

| | |
|---|---|
| 경우 열거·기댓값·선택지·해설 | `src/core/oracle.ts` — `generateOracle()` |
| 게임 전이 | `src/core/game.ts` — `askOracle()` · `resolveOracle()` · `awardOracle()` |
| 화면 | `src/ui/Oracle.tsx` — `OraclePanel` (좌표는 `LAYOUT.oracle`, 11-10절) |
| 출제 시점 | **γένεσις 후 · 융합 전.** 상점 화면처럼 core의 상태가 정한다 — `commitTurn`이 `askOracle`을 부르고, `pendingOracle`이 있으면 융합을 멈춘다. 해설을 닫는 `dismissOracle`이 융합을 실행한다 |

**각 경우의 점수는 새로 계산하지 않는다.** 그 경우로 방향을 고정한 채 `scoreBoard`를 돌리고,
떠돌이 칸의 `byCell` 항목(5-1절)을 그대로 읽는다. 미해결 #13이 이 절의 선행 조건이었던 이유다.
방향을 실제로 굴려 열거하면 융합이 쓸 난수를 미리 소모하므로, 열거는 **난수를 쓰지 않는다**
(CLAUDE.md §8). `generateOracle`이 쓰는 난수는 3지선다의 **순서 섞기 한 번**뿐이며,
`askWager`와 같은 이유로 `playRound`에서는 호출하지 않는다 — 시뮬레이터는 문항을 만들지 않는다.

**3지선다의 오답 두 개**는 표를 잘못 읽는 방식에서 순서대로 고른다: 최댓값 → 최솟값 →
기댓값의 ×1.5 → 확률을 안 곱한 합 → 기댓값의 ÷2. 정답과 같거나 이미 쓴 값은 건너뛴다.
선택지는 전부 정수이며 정답은 기댓값의 반올림이다 — 기댓값만 소수로 표시되면
**계산하지 않고도 정답이 눈에 띄기 때문이다.** 정확한 기댓값은 해설이 말한다.

#### ⛔ 점수 보너스(+50%)는 아직 배선하지 않았다 — 밸런스 결정 대기

`DRIFT_ORACLE_BONUS = 0.5`는 상수로만 존재하고, 정답 보상은 **St4RDu3t +1**만 지급된다
(9-1절). 화면도 그렇게만 안내한다.

배선 자체는 어렵지 않다 — `endTurn`이 `game.oracleCorrect`를 보고 떠돌이 칸의 `byCell` 값에

문제는 **그것이 13-6절의 목표 곡선을 통째로 밀어낸다**는 것이다. 실측:

### 8-4. CONSTELLATION LOG — 주기 종료 통계 리포트

주기 클리어 시 자동 표시.

1. **내 예측 적중률 vs 이론 확률** (막대 비교)
2. **문양별 실제 등장 횟수 vs 기댓값** (막대 비교)
3. 주기가 쌓일수록 두 값이 수렴하는 애니메이션 → **큰수의법칙** (Ⅲ-3)

> 🎪 **Phase 8 확장**: 부스 참가자 전원의 데이터를 누적해 대형 모니터에 실시간 표시.
> 표본이 커질수록 이론값에 수렴하는 것을 관객 전체가 목격 → **투표 어필 최상급 요소**

#### 기록 구조 (BOOTH-3b)

리포트가 읽을 원장은 **`GameState.wagerHistory: WagerRecord[]`** 하나다. `resolveWager`가
한 문항당 한 줄씩 덧붙이며(8-2절), 그 외에 이 배열을 쓰는 곳은 없다.

| 필드 | 내용 |
|---|---|
| `round` · `turn` | 답한 시점. 주기별 집계가 여기서 나온다 |
| `question` | 물었던 `WagerQuestion` 전체 — `text` · `answer` · `tier` · `explanation` |
| `choice` | `yes` / `no` / `abstain` |
| `correct` | 채점 결과. 기권은 항상 `false`다 |

**"내 예측 적중률"의 분모는 기권을 어떻게 셀지에 달렸다.** `choice`가 남아 있으므로 답한 것만
세는 것도, 기권을 오답으로 세는 것도 이 배열 하나로 계산된다 — **어느 쪽으로 셀지는 리포트를
만들 때 정한다.** 지금 정해 두면 화면 없이 굳는다.

> ⚠️ **시뮬레이터 실행에는 이 기록이 쌓이지 않는다.** P2 몬테카를로는 문항을 만들지 않고
> 정답률만 굴리므로(`awardWager`, 8-2절 배선표), `wagerHistory`는 **사람이 실제로 답한
> 게임에서만** 채워진다. 밸런스 측정과 학습 리포트가 서로 다른 것을 재기 때문이며,
> 이 분리가 13-6절 기준선의 재현성을 지킨다.

#### ★ 모집단 스냅샷 — 주기마다 공허를 기록한다 (BOOTH-5 확정)

리포트가 읽는 원장은 셋이다. `wagerHistory`, `drawHistory`, 그리고 **`Game.populations`**.

```ts
interface RoundPopulation {
  round:  number
  size:   number                        // 공허 장수. MЦLГЦS 조각은 두 문양을 가진 한 장이다
  bySuit: Record<SuitId, number>        // 그 문양을 가진 카드 수 = countDeck().bySuit
}
```

`startRound`가 주기당 한 줄을 남긴다. **칩 배열이 아니라 카운트만** 남긴다 — 리포트가
쓰는 것은 비율뿐이고, 공허 전체를 주기마다 복사하면 아무도 읽지 않는 상태가 된다.
난수를 쓰지 않고 점수에 영향이 없다(`tests/baseline-curve.test.ts` 9/9로 확인).

**왜 필요한가 — 현재 공허로 퉁치면 안 되는 이유가 실측됐다.**
상점이 주기 사이에 공허를 고친다(9-2절 기본 조각 매매, 13-4절 떠돌이 무상 지급).
부스판 greedy 12판에서 공허는 `50 → 52 → 52~53`으로 움직였고, 한 공허를 전 주기에
재사용하면 문양 비율이 **최대 2.64%p** 어긋난다. 그런데 부스 3주기(카드 120장)의
표본 흔들림은 약 **3.65%p**다 — **편향이 신호의 0.7배**가 되어, 리포트가 가르치려는
바로 그 흔들림과 구분되지 않는다. 그래서 주기마다 기록한다.

#### ★ 집계 규칙 (BOOTH-5 확정)

| 항목 | 규칙 |
|---|---|
| **단위** | **카드**. "이번 주기에 뽑힌 카드 중 그 문양을 가진 카드 수"를 센다. MЦLГЦS 조각 1장은 두 문양에 각각 1로, 떠돌이는 어느 문양에도 세지 않는다(3-2·3-3절) |
| **기댓값** | Σ(주기별 뽑은 카드 수 × 그 주기 모집단의 문양 비율). **누적도 주기마다 제 모집단으로** 가중한다 |
| **WAGER 분모** | **답한 문항만.** 기권은 분모에서 빼고 횟수를 따로 표시한다. 기권을 오답으로 세면 찍는 쪽이 기권보다 항상 유리해져 8-2절이 기권 버튼을 둔 이유와 반대가 된다 |
| **이론 적중률** | `WAGER_GUESS_RATE = 0.5`. 이지선다를 찍었을 때의 기대값이며, `generateWager`가 정답 쪽을 먼저 고르므로 YES/NO가 구성상 균형을 이룬다 |
| **흔한 범위** | `REPORT_BAND_SIGMA = 2` 표준편차. 비복원추출이라 실제 흔들림은 이보다 작으므로 **띠는 넉넉한 쪽으로 틀린다** — 평범한 결과를 이상하다고 부르지 않는 방향이다 |

> ⚠️ **8-1절의 `observedChances`와 섞지 않는다.** 그쪽은 **손패 단위**("그 문양이 1장 이상
> 든 손패의 비율")로, STAR-CHART와 상점이 쓰는 통계량이다. 8-4는 **카드 단위**다. 두 수치는
> 같은 색으로 그려지므로 한 화면에 함께 두면 하나의 계열로 읽힌다.
> **리포트 화면은 단위를 제목에 인쇄하고("뽑은 카드 N장 기준"), 손패 단위 수치를 싣지 않는다.**

| 집계 | `src/core/report.ts` — `buildReport()` · `RoundPopulation` · `Tally` · `ConvergencePoint` |
| 스냅샷 | `src/core/game.ts` — `startRound`이 `populations`에 한 줄, `roundReport()`가 리포트를 만든다 |
| 화면 | `src/ui/Report.tsx` — `ReportPanel` (좌표는 `LAYOUT.report`, 11-10절) |
| 표시 시점 | **`endRound` 이후 · `openShop` 이전** (4-1절). `openShop`이 떠돌이를 지급해 공허를 바꾸므로 그 앞에서 만들어야 한다. `dismissReport`가 상점을 연다 |

> **주기 번호는 `endRound` 앞에서 스냅샷한다.** `endRound`가 카운터를 먼저 올리므로,
> 그 뒤에 만든 리포트는 아직 치르지도 않은 주기의 이름을 달게 된다. 융합 화면이 턴 번호에
> 대해 하는 것과 같은 처리다(4-1절 전이는 그대로다).
>
> **리포트는 클리어했을 때만 뜬다.** 목표 미달이면 게임 오버 배너로 바로 간다 — 이 절의
> "주기 클리어 시 자동 표시" 그대로다.

#### ★ 수렴 표시 — 표본 크기를 숨기지 않는다

부스판은 3주기이고, 그 표본은 **작다**. 숨기면 화면이 거짓말을 한다.

| | 표본 | 흔들림(σ) |
|---|---|---|
| WAGER 적중률 | 15문항 | **약 12.9%p** |
| 문양 분포 | 카드 120장 | **약 3.65%p** |

그래서 셋을 화면에 넣었다.

1. **비율에는 반드시 표본 수를 붙인다.** "60%"가 아니라 **"5문항 중 3문항 (60%)"**.
2. **찍었을 때의 범위를 함께 쓴다.** 주기 1에서는 "보통 5%~95%"라고 적힌다 — 5문항으로는
   실력과 운을 가를 수 없다는 사실 자체가 표시된다.
3. **문양 막대에 흔한 범위를 띠로 깐다.** 막대가 눈금을 넘어도 띠 안이면 평범한 결과다.

**수렴은 두 줄로 보여준다** — 실제 차이(`gap`)와 그 표본에서 흔한 차이(`typical`).
`gap`은 3주기로는 흔들릴 수 있지만 **`typical`은 √표본에 반비례해 반드시 줄어든다.**
큰수의법칙 중 3주기에서도 항상 보이는 쪽이 그것이다.

> **실측 (greedy 부스판 8판, WAGER 정답률 0.7)**
>
> | 주기 | 누적 카드 | 평균 실제 차이 | 흔한 차이 |
> |---|---|---|---|
> | R1 | 40장 | 3.5% | 6.3% |
> | R2 | 80장 | 3.2% | 4.5% |
> | R3 | 120장 | **2.0%** | **3.6%** |
>
> 3주기로도 **수렴은 보인다** — 평균 실제 차이가 3.5% → 2.0%로 줄었다.
> 문양 막대 110개 중 **110개(100%)가 띠 안**에 들어왔다. 비복원추출 보정을 넣지 않은
> 띠가 넉넉한 쪽으로 틀린다는 것이 여기서 확인된다. 띠의 역할은 이상값 적발이 아니라
> **"이 정도 차이는 흔하다"**를 말하는 것이므로 이 방향이 맞다.

## 11. 아트 파이프라인 (프로시저럴 생성 방식 확정)

### 11-1. 방식

**이미지 파일을 만들지 않는다.** 픽셀맵을 코드로 정의하고 런타임에 생성한다.

```
픽셀맵 정의 (칩 32×32 배열 · 카드 36×52 · 캐릭터 60×78)
   → 같은 크기의 오프스크린 Canvas에 1px 단위로 그림
   → toDataURL()로 1회 변환 후 useMemo 캐시
   → <img> 로 표시, CSS 폭 = 원본 × 정수배 + image-rendering:pixelated
```

원본을 **정수배로만** 확대하므로 **완벽한 도트 룩**이 나오고, rect를 수천 개 그리는 성능 문제도 없다.

> **규격의 원본은 11-4절이다.** 이 절은 파이프라인만 설명하며, 원본 크기·표시 배율이
> 충돌하면 11-4를 따른다.

### 11-2. 이 방식을 택한 결정적 이유 — MЦLГЦS 조각 10종

특수 별자리 조각은 두 문양을 반반 합친 것이다. 손으로 그리면 **10장을 따로 그려야 한다.**
픽셀맵이 코드에 있으면 **합성 함수 하나로 10종이 자동 생성된다.**

**절단은 두 단계다.** 칩은 32×32이고 그 중앙 16×16이 문양이므로(11-4절), 절단선도 둘이다.

```ts
// ① 칩 전체 — 32열의 중앙, 즉 16열에서 자른다
function composeSpecial(a: SuitId, b: SuitId): PixelMap {
  const left  = CHIP[a].map(row => row.slice(0, 16));    // A 칩 좌측 16열
  const right = CHIP[b].map(row => row.slice(16, 32));   // B 칩 우측 16열
  return left.map((row, i) => [...row, ...right[i]]);
}

// ② 중앙 문양 — 문양 자체는 16×16이므로 8열에서 갈린다.
//    ①의 절단선이 문양 상자의 정중앙을 지나므로 자동으로 그렇게 된다.
```

배경·링·노치는 ①의 16열 절단으로, 중앙 문양은 그 결과로 ②의 8열 절단으로 갈린다.
링과 노치는 **세로 중심선에 대칭**이라 이음매가 보이지 않는다(11-4절).

기본 5종만 그리면 특수 10종은 공짜다. 색을 바꾸고 싶으면 상수 하나만 고치면 된다.

| **иєвυℓα** | **60×78** | **180×234px** (3배, 상점 전용 — 11-9절) |
| 문양 5종 (칩 내부) | 16×16 | 칩 중앙에 배치 |

> **칩이 16×16 → 32×32로 커진 이유**: 반지름 8px에 디테일 4겹을 넣으면 중앙에 3px만 남아
> 문양이 사라진다. 32×32의 **중앙 16×16이 정확히 기존 문양 크기**이므로,
> 칩을 키우면서 문양 5종은 한 장도 다시 그리지 않았다.

#### 칩 구조 (바깥에서 안으로)

| 겹 | 내용 | 색 |
|---|---|---|
| ① | 가장자리 노치 6개 (60° 간격) | **해당 문양의 밝은 변형색** |
| ② | 안쪽 링 1px | 바탕색의 어두운 변형 |
| ③ | 점선 원 1px | 밝은 색, 일정 간격 |
| ④ | 중앙 문양 | 기존 16×16 픽셀맵 그대로 |

노치를 크림색이 아니라 **문양별 밝은 색**으로 칠하면 카지노 칩 인상이 옅어지고,
별빛이 새어나오는 인상이 생기며, **MЦLГЦS 조각의 좌우 분할이 테두리에서도 드러난다.**

이 색 코딩은 좌우 분할의 **주 신호이지만, 10쌍 중 IMA&ACR 한 쌍에서는 성립하지 않는다.**
두 문양의 edge는 **ΔL\* 0.1**로 명도가 사실상 같고, **ΔE 19.8**은 5문양 전 조합 × 전 영역을
통틀어 최소값이다. 즉 이 한 쌍에서만 테두리가 분할을 알려주지 못하므로,
**여기서는 라벨 색 코딩이 보조 장치가 아니라 주 신호가 된다**(아래 ★절).

**측정** (`npx tsx tools/chip-contrast.mjs` · CIE76 · 원본 색 · 영역별 최소 쌍):

| 영역 | 최소 ΔE | 쌍 |
|---|---|---|
| field | 53.8 | IMA·MIM |
| edge | **19.8** (ΔL\* 0.1) | IMA·ACR |
| symbol | 29.2 | IMA·ACR |

CIE76의 JND는 2.3이다. 최소값 19.8조차 그 8배가 넘으므로 **구분 불가능한 쌍은 없다** →
**팔레트·픽셀맵은 변경하지 않는다.** 이 하한은 `tests/chip-contrast.test.ts`가 지킨다.

**MЦLГЦS 조각 합성**: 16열에서 자른다. 링·노치가 좌우 대칭이라 그대로 이어진다.
중앙 문양은 기존 규칙대로 좌 8열 + 우 8열.

#### ★ MЦLГЦS 조각 라벨의 문양별 색 코딩 (P4-A)

MЦLГЦS 조각을 **라벨과 함께 표시하는 화면**에서는, 라벨 문자열의 각 문양 부분을
**해당 문양의 잉크 색**(`SUIT_INK`)으로 칠한다. 예: `IMA&ACR` → `IMA`는 Imai 파랑,
`ACR`는 Acrux 밝은 테두리색, `&`는 중립색.

**근거**: Acrux의 필드색(`#2B2B38`)이 배경(`#0A0A12`)에 거의 묻히므로, 그 절반에서
실제로 보이는 것은 칩 표면의 1/3을 차지하는 밝은 라벤더 테두리다. 그 결과 Acrux 절반의
평균색이 보라빛으로 읽혀 Mimosa 절반과 혼동된다.

> ⚠️ **이것은 보조 장치이지 대체물이 아니다.** 칩 자체의 판독성을 라벨이 대신할 수는
> 없다 — 성단 위와 공허 구성 패널에는 라벨이 없다. 칩 판독성 자체의 처방은
> `tools/chip-contrast.mjs`의 측정 결과를 보고 따로 판단한다.

구현: `src/ui/Shop.tsx`의 `SpecialEntry`.

### 11-5. 별자리 12종 — 세로 직사각 카드

**칩이 아니다.** 36×52 픽셀맵의 **트럼프 카드 형태**이며, 표시 크기는 72×104px다.

> 32×48 → 36×52로 키운 이유는 **프레임에 2px를 확보하면서 성단 영역(26×40)을 그대로 유지**하기 위함이다.
> 성단이 줄면 별자리 형상이 무너진다.

> ⚠️ **"판정 패턴 도식" 안은 폐기됐다.** 조건의 기하 도식(점 N개를 축 방향으로 배열)은
> 판독은 되지만 우주 테마를 잃는다. 카드는 **실제 성단(星圖) 이미지**를 싣는다.

#### 카드 구성

| 요소 | 내용 |
|---|---|
| 프레임 | **2px** — 테두리 선 + 성좌 장식 + 둥근 모서리 |
| **배경** | **별하늘 픽셀 아트** (아래 참조) |
| 중앙 | 해당 별자리의 **실제 성단** |
| 별 | 십자 발광 (밝은 코어 + 4방향 팔), 등급별 크기·밝기 차등 |
| 연결선 | 별보다 어두운 청색 계열 |

#### 배경 — 카드마다 다른 별하늘

| 요소 | 내용 |
|---|---|
| 바탕 | 어두운 남보라 |
| 성점 | 불규칙 산포 — **1px 점 · 2px 십자 · 드물게 밝은 별** |
| 성운 얼룩 | 1~2군데, **카드 고유 색의 아주 어두운 변형** |

**12종이 각자 다른 하늘을 갖는다.** γένεσις는 별자리 인덱스로 시드된 난수에서 나오므로
카드를 다시 그려도 같은 하늘이 나온다(CLAUDE.md §8). 열두 장을 늘어놨을 때
한 배경의 복사본 열두 개로 보이면 안 된다.

> 🚫 **5×5 판정 격자 좌표계 안은 폐기됐다.** 성단 뒤에 게임 성단을 겹쳐 판정 셀을
> 강조하는 방식은 판독에는 도움이 되지만, 카드가 **성단이 아니라 도표**가 된다.
> 판독 문제는 아래처럼 텍스트로 푼다.

#### 프레임 장식 — 2톤 성좌

카드 고유 색에서 두 톤을 만든다.

| 톤 | 만드는 법 | 쓰는 곳 |
|---|---|---|
| 진한 톤 | 고유 색을 배경 쪽으로 약간 눌러서 | 테두리 선, 별을 잇는 연결선 |
| 연한 톤 | 진한 톤에 흰색을 섞어서 | 별의 코어, 모서리 앵커 |

테두리 둘레 전체에 별을 띄엄띄엄 놓고 연결선으로 잇는다.
**네 모서리의 별은 더 크고 밝게** 두어 앵커 역할을 시킨다.
12종이 각자 고유 색을 쓰되 **장식 패턴은 완전히 동일**하다 — 카드가 한 세트로 보여야 한다.

#### ★ 밝기 위계 (절대 규칙)

> **프레임 별의 최대 밝기 < 성단 별의 평균 밝기.**
> 프레임이 성단보다 밝으면 시선이 테두리에 뺏겨 카드를 읽을 수 없다.

이 조건은 **눈대중이 아니라 계산으로 강제**한다. 연한 톤은 카드의 성단 평균 밝기의
80% 아래로 내려갈 때까지 배경 쪽으로 단계적으로 눌린다. 테스트가 12종 전부를 검사한다.

> ⚠️ 그래서 **진한 톤은 고유 색 원본 그대로가 아니다.** 청록·호박처럼 원래 밝은 색조는
> 원본 그대로 두면 안쪽 성단과 밝기가 맞먹어 위계가 깨진다.
> 위 ★ 조건과 "원본 그대로" 지시가 충돌하므로 **★를 우선**했다.
> 색조는 유지되므로 축 식별에는 영향이 없다.

성단 자체는 **전 카드 청백색으로 통일**한다. 별자리 형상은 어느 축이 발동하는지를
전혀 말해주지 않으므로, 축 구분은 **프레임 색**이 전담한다.

#### 축 색상 코딩 — 프레임 색으로 유지

| 계열 | 별자리 | 프레임 색 |
|---|---|---|
| 세로 | 양자리 · 염소자리 · 궁수자리 | **청록** |
| 가로 | 천칭자리 · 물고기자리 · 사자자리 | **호박** |
| 대각 | 쌍둥이자리 · 황소자리 · 전갈자리 | **자홍** |
| 도형 | 물병자리 · 처녀자리 | **연보라** |
| 전역 | 게자리 | **수소적색** |

> 이 색 코딩은 밸런스와도 직결된다. 게임 시작 시 플레이어는
> **양자리(세로) / 천칭자리(가로)** 중 하나를 고르는데(10-3절),
> 축이 색으로 즉시 구분되지 않으면 그 선택이 무의미해진다.

#### ★ 판독성은 텍스트 병기로 해결한다 (절대 규칙)

성단은 "이게 무슨 별자리인가"만 말할 뿐 **연속 몇 개인지, 배율이 얼마인지는 말하지 못한다.**

> **양자리(세로 3연속)와 천칭자리(가로 3연속)는 그림만으로 절대 구분할 수 없다.**
> 두 규칙은 축만 다른데, 두 성단은 서로 닮은 구석이 전혀 없다.
> 격자 좌표계를 폐기한 이상 이 격차를 그림으로 메울 방법은 없다.

따라서 **카드를 단독으로 표시하지 않는다.**

```
[카드 이미지]
 궁수자리
 세로 5연속
 ×2.5
```

| 규칙 | 내용 |
|---|---|
| 표시 단위 | 카드 이미지 + **이름 · 조건 · 배율**이 항상 한 덩어리 |
| 구현 강제 | `ui/ConstellationCard.tsx` 하나만이 카드를 화면에 올린다. 이 컴포넌트는 텍스트를 뗄 수 없다 |
| 금지 | `PixelSprite`에 카드 픽셀맵을 직접 넘겨 단독 표시하는 것 |
| 문자열 출처 | `CONSTELLATION_RULES` · `CONSTELLATION_MULTIPLIERS`에서 파생 |

카드와 엔진이 서로 다른 규칙을 말하는 일이 없어야 한다.

> 성단 좌표는 **양식화된 성단**다. 이 크기에서 각 별자리의 알아볼 수 있는 몸짓을 살린 것이지
> 실측 천문 좌표가 아니다.

### 11-6. 떠돌이 칩 외형

**다른 조각과 완전히 동일한 칩 레이아웃**을 쓴다 — 노치 6개, 안쪽 링, 점선 원, 중앙 문양.
성단 위에서 이것은 별종이 아니라 **조각 하나**여야 하므로, 실루엣으로 구별하지 않는다.

| 요소 | 내용 |
|---|---|
| 레이아웃 | 기본 조각과 동일 (11-4절 4겹 구조) |
| 바탕 | **무지개 그라데이션** — 정해지지 않은 상태의 시각화 |
| 중앙 문양 | **왕관** (16×16, `pixels.ts`) |
| 링·문양 색 | 어두운 색 — 무지개 어느 구간에서도 대비가 확보된다 |

- 무지개는 **Ginan(적) → Gacrux(녹) → Imai(청) → Mimosa(자)** 를 잇는 연속 그라데이션이다.
  **Acrux(검정)는 제외한다** — 빛의 색이 아니고, 밴드로 넣으면 칩을 가로지르는 죽은 띠가 된다.
- 테두리·노치·점선 원도 무지개를 따라간다. 흰 테두리로 두면 노치와 점선이 칩 표면의 1/3이라
  무지개를 통째로 삼킨다.
- 6번째 기본 문양처럼 보이면 안 된다 → **왕관**이 그 역할을 한다.
  다섯 문양 중 어느 것도 아니면서 "무엇이든 될 수 있다"를 말한다.

> 초기안(육각 결정 실루엣)은 폐기했다. 실루엣을 다르게 하면 혼동은 사라지지만
> 성단 위에서 혼자 튀어 **조각이 아니라 이물질로 읽힌다.**

#### ★ 32색 예산이 세는 것 — 원색이지 파생 톤이 아니다 (확정)

|---|---|

> 그것은 33번째 색이며, 팔레트를 한 곳에서 바꾼다는 규칙도 함께 깨진다.
>
> 현재 구현이 그렇다: `NEBULA_INK`·`NEBULA_GLOW`·`TIER_COLOURS`·`AXIS_COLOURS`·
> `SUIT_INK`와 카드의 `frameTones()`는 전부 `PALETTE` 상수 + `mix()`로 계산된다.

#### ★ 이름 `иєвυℓα`는 도트로 그린다 (BOOTH-2b)

**표기는 바뀌지 않았다.** 이 절이 정한 철자 그대로다. 바뀐 것은 그것을 화면에 내보내는 방법이다.

`и є в υ ℓ α`는 키릴·그리스·필기체 el이 섞여 있어 **Galmuri에 글리프가 하나도 없다.** 텍스트로
두면 브라우저가 글자마다 시스템 폰트로 폴백해, 도트 한글 바로 옆에 매끈한 곡선 글자가 붙는다 —
화면에서 유일하게 픽셀이 아닌 문자열이 된다.

| 항목 | 위치 |
|---|---|
| 글리프 마스크 | `src/assets/pixels.ts` — `NEBULA_NAME` (35×7, 5×7 글리프 6개 + 1px 간격) |
| 색 입히기 | `src/assets/compose.ts` — `nebulaName(colour)` |
| 컴포넌트 | `src/ui/PixelWord.tsx` — `NebulaNameSprite`, `withPixelWords(line, colour)` |

- **크기는 하나만 만든다.** 노출 지점이 상점 제목과 ORION 말풍선 둘뿐이고 양쪽 다 14px이므로,
  7px 맵을 **2배**로 렌더해 14px에 맞춘다. 정수배만 쓴다(§7).
- 색은 인자로 받는다. 텍스트 한 토막을 대신하는 것이므로 들어가는 줄의 색을 따라야 한다.
- 텍스트가 아니게 되므로 래퍼에 `role="img"` + `aria-label="иєвυℓα"`를 둔다. 이미지 쪽 `alt`는
  비워, 스크린리더가 두 번 읽지 않게 한다.
- 대사는 데이터로 남긴다. `dialogue.ts`는 문자열 테이블 그대로 두고 `withPixelWords`가 렌더
  시점에 이름만 스프라이트로 바꾼다.

#### ★ γένεσις · πειρασμός · MЦLГЦS도 도트로 그린다 (BOOTH-9a)

2-3절의 용어 개편이 그리스어·키릴 문자를 UI 본문으로 끌어들였다. 위와 **같은 파이프라인**을
쓴다 — 새 파이프라인을 만들지 않는다.

**이유는 "Galmuri에 글리프가 없다"가 아니다 — 실측이 그것을 부정했다.**
woff2 cmap을 직접 읽어 보면 **Galmuri9와 Galmuri11은 세 단어의 모든 글자를 갖고 있다.**
없는 것은 **Galmuri14와 Galmuri11-Bold**다(글리프 12,695개 대 Galmuri11의 20,965개).
그리고 `index.css`는 본문 크기 `text-sm`을 Galmuri14로, 모든 굵은 제목을 Galmuri11-Bold로
보낸다. 즉 **타이핑하면 같은 단어가 패널에 따라 도트였다가 시스템 폰트였다가 한다.**

| 크기 클래스 | 서체 | 세 단어 |
|:--|:--|:--|
| `text-[9px]` · `text-lg` | Galmuri9 | 도트 — **타이핑한다** |
| `text-[11px]` · `text-[22px]` · `text-[44px]` | Galmuri11 | 도트 — **타이핑한다** |
| `text-sm` · `text-[42px]` | Galmuri14 | **폴백 → 스프라이트** |
| 굵은 `text-[11px]` · `text-[22px]` | Galmuri11-Bold | **폴백 → 스프라이트** |

`tools/font-fallback.mjs`가 이 표를 매번 다시 만든다. **판정은 단어가 아니라 서체의 속성**이고,
서체는 크기 클래스가 고른다 — 그래서 크기별로 걷는 것 외에 정직한 검사가 없다.

**단어 단위가 아니라 글자 단위로 만든다.** ε·σ·ς·ι·α는 두 단어 이상에 나오고,
두 번 그린 글자는 어긋난다. 고유 글자는 **17자**다:

`γ έ ν ε σ ι ς` · `π ρ α μ ό` · `M Ц L Г S` — (ε·σ·ς·ι는 두 단어 공용, α는 иєвυℓα에서 그대로 가져옴)

| 항목 | 위치 |
|---|---|
| 글리프 표 | `src/assets/pixels.ts` — `PIXEL_GLYPHS` (5×9 셀 17자) |
| 단어 조판 | `src/assets/pixels.ts` — `pixelWord(word)` (1px 자간) |
| 색 입히기 | `src/assets/compose.ts` — `pixelWordMap(word, colour)` |
| 컴포넌트 | `src/ui/PixelWord.tsx` — `PixelWordSprite`, `withPixelWords(line, colour)` |

**셀 규격 5×9와 그 근거 (실측)**

```
행 0      대문자 상단
행 1      악센트(έ ό) · 대문자
행 2–6    x-height                ← иєвυℓα와 같은 다섯 행
──────    베이스라인 (행 7)
행 7–8    디센더 (γ ρ μ ς, Ц의 꼬리)
```

2배로 쓰므로 한 행이 화면 2px이다. Galmuri14 @14px를 래스터라이즈해 잉크를 재면:

| 항목 | Galmuri14 실측 | 이 표 ×2 | 행 | 차이 |
|---|--:|--:|--:|---|
| x-height | 10px | 10px | 5 | **정확히 일치** |
| 대문자 높이 | 13px | 14px | 7 | +1px |
| 디센더 | 3px | 4px | 2 | +1px |
| 악센트 상단 | 11px | 12px | 1 | +1px |

정수배는 짝수 높이만 낼 수 있고 13·3·11은 홀수라 나머지 셋은 1px을 줄일 수 없다.
**x-height만은 정확해야 하고 실제로 정확하다** — 한 줄의 모든 소문자가 공유하는 값이라
어긋나면 눈에 바로 보인다. 악센트는 초안에서 두 행(14px)이었고, 그러면 대문자와 옆 한글보다
높이 솟는다. 한 행이 그 수정이다.

- 모든 획은 **1px**, 정수배만(§7).
- `aria-label`에 원문 단어를 둔다 — 스크린리더와 복사·붙여넣기가 진짜 글자를 얻는다.
- 문자열 테이블은 **원문 그대로** 두고 렌더 시점에만 치환한다(`dialogue.ts` 방식).
- 검수는 `npx tsx tools/glyph-proof.mjs` → `tools/out/glyph-proof.html`
  (낱자 10배 · 단어 6배 · 14px 본문 인라인 비교, 베이스라인/​x-height 가이드선 포함).

> ⚠️ **알려진 미달**: 상점 그룹 라벨은 굵은 11px(Galmuri11-Bold)이라 스프라이트가 필요한데,
> 그 서체의 x-height는 8px이고 5행에 맞는 정수배가 없다. 2배(10px)를 써서 옆 한글보다
> **1/4 크게** 나온다. 대안은 그 라벨의 굵기를 빼거나(Galmuri11로 내려가 타이핑 가능),
> 세 글자를 시스템 폰트로 두는 것뿐이다.

### 11-10. ★ 화면 레이아웃 — 고정 캔버스 (절대 규칙)

**게임 화면은 1120×630 고정 캔버스다. 유동 웹 레이아웃으로 되돌리지 않는다.**

#### 왜 고정인가

유동 레이아웃에서는 크기가 픽셀로 박힌 요소(성단)만 제자리를 지키고 나머지는 flex 여백을 따라

**참여자마다 다른 화면을 보게 된다.** 요소를 개별 이동해서는 해결되지 않는다 — 레이아웃이
유동이기를 그만두어야 한다. 부스는 서로 다른 노트북 3대 이상으로 운영되므로(12-2절)
**모든 기기에서 같은 그림**이 나오는 것이 요구사항이다.

#### 방식

| 항목 | 값 |
|---|---|
| 논리 캔버스 | **1120×630** (16:9) |

**파비콘 32·16은 56을 축소한 것이 아니다.** 56/32와 56/16이 정수가 아니라 축소하면 팔이
픽셀 사이에 놓인다(§7). 그래서 별의 좌표·반지름을 **상자 크기의 분수**로 적어 두고
32·16에서 같은 식을 다시 평가한다 — 세 크기가 정의상 같은 마크가 된다.
배경은 채운다: 탭 스트립은 브라우저의 색이고, 흰 바탕 위의 창백한 파랑 넷은 보이지 않는다.

#### 5단계 — 한 단계는 하나만 가르친다

| # | 뜨는 시점 | 가리키는 곳 | 가르치는 것 | 사라지는 조건 |
|---|---|---|---|---|
| 1 `wager` | 시작 직후 (WAGER 모달 위) | 문항 | 확률 문제이고 틀려도 손해가 없다 | YES/NO를 누르면 |
| 2 `hand` | 첫 손패가 내려온 뒤 | 손패 부채 | 칩을 고른다 | 칩을 고르면 |
| 3 `board` | 칩을 든 상태 | 성단 | **어떻게 놓으면 배율이 붙는가** | 첫 칩을 놓으면 |
| 4 `limit` | 1장 놓은 뒤 | 손패·γένεσις 카운터 | 턴당 4장, 다 놓으면 턴 종료 | 턴 종료를 누르면 |
| 5 `target` | 첫 융합 중 | 이번 주기 누적·목표 | 5턴 안에 목표를 넘겨야 한다 | 다음 턴을 누르면 |

**「다음」 버튼이 없다.** 각 단계는 **가르치려는 그 동작**으로만 사라지므로, 읽기 싫은 학생은
그냥 조작하면 지나간다. 코치마크는 `pointer-events-none`이고 어떤 클릭도 삼키지 않는다.

**건너뛰기 버튼을 두지 않는다.** 1인 운영에서 그 버튼은 학생이 가장 먼저 누르는 것이 되고,
건너뛴 학생이 곧 운영자를 부른다. 대신 **강제도 아니다** — 5단계를 전부 무시해도 게임은 정상
진행되며, 강제되는 것은 8-2절의 WAGER 3회뿐이다.

#### 3단계 문구는 시작 별자리에서 파생한다

13-5절이 시작 선택 2종을 **축만 다르게** 둔 것이 이유다. `세로로 3개`를 박아 넣으면 천칭자리를
고른 절반에게 틀린 축을 가르친다. 문구는 카드가 인쇄하는 것과 같은 두 함수
(`conditionOf` / `multiplierOf`)로 만든다 — 양자리면 `같은 문양 세로 3연속 이상이면 ×1.2`,
천칭자리면 `같은 문양 가로 3연속 이상이면 ×2.1`.

|---|---|
| `localStorage` | 부스 노트북은 학생마다 새로 로드되지 않는다. **2번째 학생이 튜토리얼을 못 본다** |
| 메모리 플래그 (페이지 로드당 1회) | 같은 문제. `타이틀로`가 리셋이므로 로드는 하루에 한 번이다 |
| **매 런의 1주기** ✅ | 새 학생이 튜토리얼을 놓치는 사고가 원천 차단된다 |

같은 학생이 두 번 플레이하면 두 번 본다. 각 단계가 동작 한 번으로 사라지므로 비용은 실질 0이고,
**튜토리얼을 못 본 학생이 운영자를 부르는 쪽이 훨씬 비싸다.**

> **상태를 저장하지 않는다.** 어느 단계인지는 화면이 이미 들고 있는 상태의 순수 함수다
> (`src/ui/Coach.tsx` — `coachStep`). 그래서 코치마크가 게임과 어긋날 수 없고 `src/core/`가
> 튜토리얼의 존재를 알 필요가 없다 (CLAUDE.md §5).

#### 재진입 — ESC 퍼즈 창의 `튜토리얼 시작` (BOOTH-9c 확정)

5줄 요약 **1장을 정지 화면으로** 띄운다. **코치마크를 재생하지 않는다** — 헤맨 학생이 원하는
것은 "처음부터"가 아니라 "지금 뭘 해야 하나"이고, 5단계 중 3개는 재현 불가능하다(첫 문항은
답했고 첫 융합은 끝났다). 요약과 코치마크는 같은 문구를 공유한다(`ui/Coach.tsx` — `HelpCard`).

요약 카드는 **모든 주기에서** 열 수 있다. 코치마크는 1주기만이므로, 2주기 이후의 유일한 안내다.

> ⚠️ **`?` 버튼(1012, 12) 28×28은 없다.** BOOTH-9b가 그 자리를 STAR-CHART에 내주면서 지웠다.
> 카드 자체는 손대지 않았고, **바뀐 것은 여는 사람**이다 — BOOTH-9c부터는 ESC 퍼즈 창의
> 두 번째 항목이 연다. 좌표표는 11-10절.
>
> **`튜토리얼 시작`이라는 이름과 "재생하지 않는다"는 규정이 어긋나 보인다.** 이름은 BOOTH-9c
> 지시문이 정한 것이고 동작은 위 규정 그대로다. 재검토 대상으로 남긴다 — 대안은 `게임 방법`.
>
> **중도 리셋도 같은 창에 있다 (BOOTH-9c).** 12-2-c · 12-2-d 참조.

### 12-2-b. ★ 부스 빌드는 모드를 하나만 내놓는다 (BOOTH-7 확정)

**타이틀 화면의 모드 목록을 빌드 시점에 결정한다.** 정본은 `src/ui/Title.tsx`의
순수 함수 `modeOrder(prod, unlocked)`이고, 호출부는
`modeOrder(import.meta.env.PROD, fullUnlocked())` **하나뿐**이다.

| 환경 | 보이는 모드 | 근거 |
|---|---|---|
| `npm run dev` (개발) | 부스판 + 풀버전 | 개발·`npm run shot`이 두 모드를 다 쓴다. 켜야 할 플래그가 없어야 한다 |
| 프로덕션 빌드 (부스 노트북) | **부스판만** | 풀버전 8주기 ≈ 40분. 12-1절 기준 좌석 하나가 표 하나를 잃는다 |
| 프로덕션 빌드 + `?mode=full` | 부스판 + 풀버전 | 시연·검증용 탈출구. 학생이 우연히 칠 수 없다 |

**빌드 시점을 고른 이유 — 대당 편차가 생길 수 없어야 한다.**
부스 노트북은 3~5대이고 운영자는 1명이다(12-1절). `.env`·`localStorage` 같은 런타임
설정은 **대당 설정**이 되고, 한 대만 잘못 켜져 있어도 그 좌석이 40분 점유되며 그것을
알아챌 사람이 없다. `import.meta.env.PROD`는 배포 산출물 자체가 결정하므로 이 사고가
구조적으로 불가능하다.

**풀버전을 지우지 않는다.** 12-2 ③의 옛 서술("`TOTAL_ROUNDS`와 `TARGET_SCORES`만
교체")은 코드를 갈아 끼우는 방식인데, 그러면 개발·시연에서 풀버전이 사라지고
13-6절의 풀버전 측정도 재현할 수 없게 된다. **숨기되 남긴다**가 확정안이며,
열쇠는 `?mode=full`이다 — `?seed=`(`src/store/gameStore.ts`)가 이미 같은 방식의
탈출구이므로 규약을 새로 만들지 않았다.

> 부스판이 어느 빌드에서든 **목록의 첫 항목**이다. 타이틀 화면의 기본 선택이 첫 항목이므로,
> 이 순서가 깨지면 분기 자체가 무의미해진다. `tests/booth.test.ts`가 네 조합 전부에서
> 이것을 검사한다.

### 12-2-c. ★ 중도 리셋 (12-2 ④ · BOOTH-7 확정 · BOOTH-9c 분리)

| 항목 | 확정 |

| 어느 화면에 | ⚠️ **상점만.** 게임 화면의 통로는 ESC 퍼즈 창이다 (BOOTH-9c, 12-2-d) |

#### ★ `다시 시작`과 `처음 화면으로`는 다른 것이다 (BOOTH-9c 확정)

퍼즈 창은 이탈 경로를 **둘**로 나눈다. 둘 다 지금 판을 버리지만 그 다음이 다르다.

| 항목 | `다시 시작` | `처음 화면으로` |
|---|---|---|
| 다음에 오는 것 | **같은 모드·같은 시작 별자리로 곧장 새 판** | 타이틀 화면 (모드·시작 별자리를 다시 고른다) |
| 호출 | `gameStore.newGame()` — `setup`을 유지한다 | `gameStore.toTitle()` |
| 누가 쓰나 | 망친 판을 다시 하려는 **같은 학생** | 자리를 비우는 학생, 또는 기계를 정리하는 운영자 |
| 확인 제목 | `같은 설정으로 다시 시작할까요?` | `처음 화면으로 돌아갈까요?` |
| 확인 본문 | `지금 판은 사라집니다. 되돌릴 수 없습니다.` | `지금 판은 사라지고 시작 화면이 열립니다.` |
| 확인 버튼 | `계속하기`(강조) · `다시 시작` | `계속하기`(강조) · `처음 화면으로` |
| 정본 | `RESTART_CONFIRM` | `TITLE_CONFIRM` |

**확인 제목이 서로 다른 이유.** 두 항목이 세로로 붙어 있으므로 **이름만으로는 구별이 안 될 수
있다** — 중학생에게 "다시 시작"과 "처음으로"는 같은 말로 읽힌다. 그래서 확인 제목이 *무슨 일이
일어나는지*를 한 번 더 말한다. 본문(잃는 것)이 같은 것은 실제로 같기 때문이다.

**확인 버튼이 항목 이름을 그대로 되풀이하는 것은 BOOTH-7의 규칙 그대로다** — 동의하는 대상을
그 일을 하는 버튼에 적는다. 상점의 `처음으로`와 퍼즈 창의 `처음 화면으로`가 다른 낱말인 것도
같은 규칙의 결과다: 각 화면에서 눌린 이름이 확인 버튼에 그대로 나온다.

> **코치마크는 `다시 시작` 뒤에도 다시 뜬다.** 12-2-a의 첫 플레이 판정이 "런의 1주기"이므로
> 자동으로 성립한다. `tests/pause.test.ts`와 실기 확인이 이것을 본다.

**확인 단계를 둔 이유**: 이탈 항목이 도움말 바로 옆에 있다. BOOTH-7에서는 `처음으로`가 `?`
옆이었고, BOOTH-9c에서는 퍼즈 창 안에서 `튜토리얼 시작` 바로 아래가 `다시 시작`이다. 12-2-a가
도움말을 "헤맨 학생이 누르는 것"으로 정의했으므로 헤맨 학생이 그 근처를 더듬는 것이 정상
동작이고, **오조작이 예외가 아니라 전제**다. 한 번의 오조작이 20분을 날린다.

**`계속하기`가 강조 버튼인 이유**: 두 선택지의 비용이 비대칭이다 — 계속하기는 아무것도
잃지 않고, 나머지 하나는 런을 끝낸다. 눈이 먼저 닿는 쪽을 비용이 없는 쪽에 둔다.
**숨기지는 않는다** — 나가려는 학생에게는 이름이 붙은 버튼 하나가 그대로 보인다.

**상점이 자기 버튼을 갖는 이유**: 상점은 한 런에서 2회(부스판) 뜨고 12-1절 기준 3.7분을
차지한다. 그 사이에 포기한 학생이 남긴 화면도 운영자가 F5를 눌러야 하는 화면이다.
퍼즈 창은 게임 화면에만 있으므로(12-2-d) 상점의 코너 버튼이 그 3.7분의 유일한 통로다.

> **상점에는 퍼즈 창을 두지 않았다.** 상점에는 이미 이름이 붙어 **보이는** 버튼이 있고,
> 12-2-a는 도움말을 "모든 주기에서" 보이라고 하면서도 상점에 `?`를 둔 적이 없다. 여기에
> 퍼즈를 붙이면 같은 기능이 두 벌 생긴다. 상점의 이탈 경로가 부족하다는 근거가 나오면
> 다시 본다.

> **코치마크가 다시 뜨는 것이 정상이다.** 12-2-a가 첫 플레이 판정을 "런의 1주기"로
> 정한 이유가 정확히 이 경우다 — 리셋 뒤에 오는 학생은 새 학생이다.
> `tests/booth.test.ts`가 리셋 → 새 런에서 `coachStep`이 다시 `wager`를 내는지 검사한다.

#### ESC 우선순위 — **ESC는 퍼즈 창의 것이고, 다른 무엇의 것도 아니다**

| 상태 | `ESC` |
|---|---|
| 닫혀 있음 | 연다 |
| 하위 페이지(요약·설정·확인) | 메뉴로 한 단계 되돌린다 |
| 메뉴 | 닫는다. 게임은 있던 자리 그대로 |

**BOOTH-9b의 "열린 것을 먼저 닫고, 없을 때만"은 폐기했다.** 그 규칙은 ESC의 마지막 동작이
파괴적이었기 때문에 있었다. 지금 ESC는 첫 항목이 `계속하기`인 메뉴를 열 뿐이므로 막을 것이 없다.

**★ 게임 모달은 ESC로 닫히지 않고, ESC를 막지도 않는다.** WAGER·ORACLE·LOG는 그대로 있고 퍼즈
창이 그 **위에** 덮는다. 창을 닫으면 같은 질문 앞으로 돌아온다.

> **강제 WAGER 구간(8-2절, 3회)이 이 규칙의 시험대다.** 두 가지 실패가 가능했다.
> ① ESC가 WAGER를 닫아 버리면 강제 구간이 무너진다 ② 모달이 떠 있는 동안 ESC를 무시하면
> 헤맨 참여자가 **자기 첫 세 문항 안에 갇혀** 런을 포기할 수 없게 되는데, 이것이 정확히
> 12-2 ④가 금지하는 상태다.
> **덮되 닫지 않는 것**이 둘을 한꺼번에 만족한다 — 문항은 답해지지 않은 채로 남고,
> `처음 화면으로`는 강제 구간 안에서도 닿는다. 실기로 확인했다.

#### 설정 — **실제로 제어되는 것만 넣는다**

| 항목 | 값 | 무엇이 바뀌나 |
|---|---|---|
| **애니메이션** | `켜기` / `끄기` | 끄면 융합 걷기(문양당 600ms)와 카드 발동 연출, 칩 비행·스태거가 사라진다. 점수는 그대로, 턴은 더 빨리 넘어간다 |

- **기본값은 `prefers-reduced-motion`이 정한다.** OS가 감축을 요구하면 `끄기`로 시작한다.
  그 뒤로는 **스위치가 답이다** — OS 설정을 그 위에 덧씌우면 학생이 방금 고른 `켜기`가
  아무것도 하지 않게 되고, 그것이 곧 "아무것도 제어하지 않는 항목"이다.
- **세션 안에서만 유지한다. `localStorage`를 쓰지 않는다.** 12-2-a가 코치마크 판정에서 기각한
  것과 같은 이유다 — 부스 노트북은 학생마다 새로 로드되지 않으므로, 저장된 설정은 **앞 학생의
  설정을 다음 학생에게 물려주는 것**이 된다. `다시 시작`은 같은 학생이므로 유지한다.
- **2초 대기는 줄이지 않는다.** 근거는 5-1절.

**넣지 않은 것과 그 이유 — 사운드가 들어오면 첫 줄은 재검토 대상이다.**

### 12-4. 부스 모드의 밸런스 철학은 풀버전과 정반대다

| | 풀버전 | 부스판 |
|---|---|---|
| 목표 클리어율 | **20 ~ 30%** (도전) | **70% 이상** (만족) |
| 최적화 대상 | 재도전 욕구 | **투표** |

부스 참여자는 단 한 번 플레이하고 투표한다. 실패하고 떠나면 표를 잃는다.

> **판정 기준은 개별 숫자가 아니라 클리어율이다.**
> 초기 문구는 "상향 금지"였으나, 이는 개별 목표값이 아니라 **난이도**를 뜻한다.
> 실제 확정안에서 R2는 500 → 630으로 올랐지만, 기존 300·500은 바닥값 600보다 낮아
> 아무도 탈락시키지 못하는 장식이었고 실질 관문은 R3(800) 하나뿐이었다.
> R3를 640으로 크게 낮춘 결과 greedy 클리어율이 **28.4% → 72.3%** 로 개선됐으므로
> 규칙의 취지는 지켜졌다.
>
> (이 두 수치는 떠돌이 가격 10 시점의 측정이다. 무상 지급까지 반영한 최종값은 **85.3%** 다 — 13-6절.)

#### ★ 70% 조항은 이제 봇 기준으로는 성립하지 않는다 (BOOTH-9a)

부스 곡선이 **[600, 900, 2000]** 으로 확정되면서 greedy 클리어율이 85.3% → **0.2%** 가 됐다
(10-4절). 위 표의 "70% 이상"과 정면으로 어긋난다.

**이 절의 수치는 유지한다.** 목표 곡선은 설계자가 직접 플레이해 확정한 값이고, 난이도를
극한으로 잡은 것이 의도이기 때문이다. 대신 어긋남의 성격을 분명히 적어 둔다.

| | 내용 |
|---|---|
| 70%를 재는 주체 | `sim/player.ts`의 **greedy 봇** — 한 턴 앞만 보고 즉시 점수를 최대화한다 |
| 재지 못하는 것 | STAR-CHART를 읽고 두 턴 앞을 계획하는 **사람**의 실력 |
| 그래서 남는 질문 | 사람 기준 클리어율은 얼마인가 — **미측정** |

> 봇 수치를 사람 수치로 읽으면 안 된다. 그 간극이 얼마나 큰지는 아직 재지 않았고,
> 이 곡선이 부스에서 실제로 어떻게 작동하는지는 **현장 관측이 정본**이 된다.
> 봇 기준 재측정으로 곡선을 되돌리지 않는다.

#### ★ 종료 화면이 투표를 언급한다 (BOOTH-7)

12-1절이 "처리량이 곧 성적"이라고 적고 이 절이 "실패하고 떠나면 표를 잃는다"고 적었는데,
**게임은 투표를 한 번도 언급하지 않았다.** 28분을 쓰게 하고 아무것도 부탁하지 않은 것이다.
종료 배너(클리어·게임오버 양쪽)에 한 줄을 넣었다.

| | 문구가 하는 일 |
|---|---|
| 클리어 | 부탁 한 문장. 앞에 덧붙일 것이 없다 |
| 게임오버 | **런을 닫는 반 문장 + 같은 부탁.** 이 절이 "실패하고 떠나면 표를 잃는다"고 한 바로 그 학생이 읽는 화면이므로, 부탁이 "졌으니 표를 달라"로 읽히면 안 된다 |

**두 문구의 차이는 앞 반쪽뿐이고 부탁 자체는 같은 문장이다.**

> ⚠️ **문구는 placeholder다. 투표 방식이 확정되지 않았다.**
> 정본은 `src/ui/Game.tsx`의 `VOTE_NOTE` 두 문자열이고, 방식이 정해지면 그것만 갈아 끼운다.
> **QR 코드는 넣지 않았다** — 가리킬 곳이 없는 QR은 마지막 화면에 놓인 죽은 링크이고,
> 그것은 안내가 없는 것보다 나쁘다. `tests/booth.test.ts`가 두 문구에 URL·QR이
> 섞여 들어가지 않았는지, 그리고 둘 다 투표를 실제로 언급하는지 검사한다.

### 12-5. ★ 부스판 WAGER 보정 원칙 (신규)

풀버전 측정에서 WAGER 정답률 0% ↔ 100%의 클리어율 차이가 **27.0%p**로 나타났다.
학습 행동이 승패에 유의미해진 것은 성과지만, **부스판에 그대로 적용하면 재앙이다.**

> 부스 참여자는 **확률을 배우러 온 중학생**이다.
> 확률 문제를 못 맞혀서 탈락한다면, 게임이 가르치려는 바로 그 대상을 걸러내는 것이다.

따라서 두 버전에 **서로 다른 원칙**을 적용한다.

| | 풀버전 | 부스판 |
|---|---|---|
| WAGER의 역할 | 승패를 가르는 실력 요소 | **순수 상방(bonus)** |
| 목표치 보정 기준 | smart 기본 정답률(80%) 기준 | **WAGER 정답률 0% 기준으로 70% 클리어** |
| 근거 | 반복 플레이어 대상 | 1회 플레이 + 학습 대상자 |

**즉 부스판 목표치는 "확률을 하나도 못 맞혀도 70%가 클리어"하도록 잡는다.**
확률을 잘 맞히는 학생은 더 여유롭게 클리어할 뿐, 못 맞히는 학생이 탈락하지는 않는다.
이것이 교육용 게임과 실력 게임을 가르는 지점이다.

#### ✅ P2-B 측정 결과 — 현행 목표치가 이미 원칙을 만족한다

| tier (sum) | WAGER 0% | WAGER 50% | WAGER 100% |
|---|--:|--:|--:|
| greedy | **71.3%** | 85.0% | 87.2% |
| smart | 94.7% | 94.2% | 94.2% |

`[490, 630, 640]` 그대로 기준을 충족하므로 **재역산하지 않는다.**
부스판에서 WAGER는 71.3% → 87.2%의 **순수 상방**으로 작동한다.

대조군으로 풀버전은 smart 기준 4.2% → 40.4%(+36.2%p)다. 같은 장치가 버전에 따라
전혀 다른 역할을 하며, 그것이 이 절을 따로 둔 이유다.

### 13-1. P2 시뮬레이터가 반드시 포함해야 할 케이스

**① 단일 문양 도배 성단 + 물병자리·처녀자리 동시 보유**
꼭짓점이 다르면 별개 라인이므로, 5×5를 한 문양으로 채우면
ㅅ자 약 12개 + ㅗ자 약 15개가 동시 발동할 수 있다. 각 라인이 `(칸수 × 10) × 배율`을 받으므로

> ✅ **해소** (`tests/gdd13-1.test.ts`): ㅅ자 12개 + ㅗ자 12개가 동시 발동해도
> 물병+처녀 2,432점 vs 궁수+사자 1,250점으로 **1.95배**에 그친다. 네 별자리 전부라도 3,662점.

**② 떠돌이 조각 + MЦLГЦS 조각 3개 인접**

### 13-4. 떠돌이 조각 가격 — 교육적 근거로 인하

측정 결과 St4RDu3t 1당 기여가 최상 2.5 / 보통 1.5 / 최악 0.5점·턴으로,
기본 조각(3.3)보다 **나쁘다.** 가격 20은 순수 효율로는 명백한 과다다.

그런데 여기엔 점수 효율보다 중요한 이유가 있다.

> **떠돌이 조각을 사지 않으면 `DRIFT ORACLE`(GDD 8-3)이 게임 내내 한 번도 발동하지 않는다.**
> 이 장치는 교과서 Ⅲ-2 **기댓값**을 가르치는 유일한 수단이며,
> 4개 학습 장치 중 확률 개념이 가장 직접적으로 드러나는 순간이다.

즉 이 아이템의 가격은 **밸런스 문제가 아니라 학습 노출률 문제**다.
학생이 "비싸서 안 삼" → 기댓값 단원이 통째로 사라진다.

#### P2-B 결과: 인하는 과잉 교정이었다

| 지표 | 가격 20 | 가격 10 |
|---|---|---|
| 구매율 | 28.3% | **98.6%** |
| 미구매 시 클리어율 | — | **0.0%** (전 등급) |

학습 노출률 목표는 달성했으나, **선택이 아니라 세금**이 됐다.
98%가 첫 상점에서 즉시 구매하므로 "게임당 1회 한정"이라는 희소성 연출도 무의미하다.
더 심각한 것은, 이해 못 하고 안 산 학생은 **그 시점에 이미 게임이 끝난다**는 점이다.

#### 확정: 구매가 아니라 무상 지급

**иєвυℓα와의 첫 만남에서 떠돌이 조각을 무상으로 지급**한다.

| 효과 | 내용 |
|---|---|
| DRIFT ORACLE 발동률 | 98.6% → **100%** |
| 가짜 선택지 제거 | St4RDu3t가 실제 의사결정에 쓰인다 |
| 목표 곡선 유효성 | 시뮬 전제(98.6% 보유)와 사실상 동일 → **재보정 불필요** |
| 서사 | 딜러가 첫 거래 기념으로 건네는 선물 |

`SHOP_PRICES`의 떠돌이 항목을 제거하고, 상점 진열에서도 뺀다.

> **P4-A 보강**: `SHOP_SLOTS.drifterChips`가 남아 있던 것을 함께 제거했다.
> `rollStock`이 읽지 않아 무해했지만, 죽은 설정값은 나중에 되살아나 이 절을 조용히 깨뜨린다.
> 떠돌이는 **재고가 아니라 선물**이므로 진열 칸이라는 개념 자체가 없어야 한다.

### 13-5. 🚨 R1은 플레이어 행동과 무관하다

R1 점수는 **모든 등급에서 정확히 600점, 표준편차 0**이다.
별자리는 R1 클리어 후 상점에서만 살 수 있는데, 별자리가 없으면 라인이 발동하지 않아
점유 칸수 × 10의 합(40+80+120+160+200)만 남기 때문이다.

| 문제 | 영향 |
|---|---|
| 실력·확률 판단이 점수에 **0** 반영 | 첫 5턴 동안 피드백 루프가 없다 |
| 첫인상 구간 | 부스 참여자가 게임을 판단하는 바로 그 5턴 |
| 별자리 개념 미노출 | 게임의 핵심 시스템을 R2에야 처음 본다 |

#### 처방: 시작 별자리 1개 지급

게임 시작 시 **양자리(세로 3연속, ×1.2) / 천칭자리(가로 3연속, ×1.2) 중 1개를 선택**하게 한다.

- 두 별자리는 배율이 같고 축만 다르다 → 밸런스 영향 없이 **"세로냐 가로냐"** 라는 첫 의사결정이 생긴다
- 별자리 시스템을 R1부터 체험한다
- R1 점수에 변동성이 생겨 γένεσις 실력이 즉시 피드백된다
- 보유 한도 4개 중 1칸을 채우고 시작한다

> 이 변경은 R1 목표치 재산정을 동반한다. 13-3절 기준에 함께 반영한다.
